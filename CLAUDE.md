## Фронтенд

Два инструмента закрывают две разные задачи: `ui-ux-pro-max` отвечает на вопрос
«как это должно выглядеть» до написания кода, `playwright-cli` - на вопрос «что
получилось на самом деле» после. Один не заменяет другой, и оба бесполезны для
логики без визуальной части.

### `ui-ux-pro-max`: чем и как оформлять

**Что решает.** Не даёт придумывать оформление на глаз и по памяти. Это локальная
база решений (стили, палитры, шрифтовые пары, типовые продукты, UX-правила,
моушен, графики) плюс генератор дизайн-системы под конкретный стек. Вместо
«выбрал синий, потому что синий» получается обоснованный набор токенов и правил,
одинаковый во всех сессиях.

**Когда обязателен.** Новая страница или компонент, изменение вёрстки, выбор
цвета, типографики, отступов, анимации, работа с доступностью, ревью
интерфейса - то есть всё, что меняет вид, ощущение, движение или способ
взаимодействия.

**Когда не нужен.** Хуки, API-клиент, типы, роутинг, обработка ошибок без UI:
там он только добавит шума.

**Как пользоваться.** Скилл лежит в `.claude/skills/ui-ux-pro-max`, поиск идёт
через его Python-скрипт:

```bash
# дизайн-система под задачу (первый шаг для новой страницы)
python .claude/skills/ui-ux-pro-max/scripts/search.py "internal platform dashboard" --design-system
# точечный запрос по домену: ux, color, typography, style, product, gsap, chart, icon
python .claude/skills/ui-ux-pro-max/scripts/search.py "empty state" --domain ux
```

Категории в скилле упорядочены по важности: доступность и попадание в тип
продукта идут раньше красоты. Если рекомендация скилла конфликтует с правилами
этого файла (тексты интерфейса, запрет длинного тире), выигрывают правила файла.

### `playwright-cli`: смотреть, что получилось

**Что решает.** Тайпчек, biome и юнит-тесты ничего не знают о том, как страница
выглядит и падает ли она в браузере. Playwright Agent CLI даёт браузер обычными
shell-командами: страница отдаётся деревом доступности с ссылками на элементы,
поэтому её можно читать и кликать без скриншотов и без тяжёлых схем инструментов
в контексте.

**Когда звать.** После любой правки интерфейса. При разборе жалобы «не
работает» - посмотреть своими глазами, а не по описанию. Когда нужно понять, что
реально уходит в API и что отвечает бэкенд. Когда правка видна только в узком
окне или только у определённой роли.

**Базовый цикл.**

```bash
playwright-cli goto <url>     # открыть страницу
playwright-cli snapshot       # дерево доступности с ref'ами элементов
playwright-cli click e12      # действия по ref из снимка
playwright-cli console        # ошибки рантайма
playwright-cli screenshot     # картинка, когда важен сам вид
```

Полезное сверх цикла: `find "текст"` вместо полного снимка на больших
страницах, `resize` для узких экранов, `route` для мока ответов API,
`state-save`/`state-load` для переиспользования входа, `requests` и `response-body`
для разбора сетевого обмена. Справочники по трейсам, видео и генерации тестов
лежат в `.claude/skills/playwright-cli/references`.

**Дешевизна.** Снимок дерева - это текст, он на порядок дешевле скриншота и
пригоден для diff'а. Скриншот нужен, только когда вопрос именно в том, как это
выглядит.

### Правила этого проекта

- **Пакетный менеджер для `web/` - только `bun`, не `npm`/`npx`.** Используй `bun install`, `bun run <script>`, `bunx <tool>`. Лок-файл - `bun.lock` (в репозитории; `package-lock.json` не держим). Так же настроены lefthook (`bun run typecheck`, `bunx biome`) и сборка SPA в корневом `Dockerfile` (стейдж `oven/bun`, бандл вшивается в portal через `go:embed`, см. `internal/spa`).
- **Playwright ставится один раз глобально:** `bun add -g @playwright/cli`, затем `playwright-cli install --skills` в корне репозитория (браузер подхватывается системный, иначе `playwright-cli install-browser chrome`). Рабочие каталоги `.playwright/` и `.playwright-cli/` (снимки, скриншоты, трейсы, сохранённое состояние входа) не коммитятся.
- **Смотреть нужно на Vite (http://localhost:5173), а не на порт портала.** Только там работает проксирование `/api` и совпадает origin, на который настроен OIDC-редирект. Стенд поднимается как для разработки: `make infra`, `make run-oidc`, `make web`.
- **Вход настоящий, через Keycloak.** Пользователи стенда: `alice/alice` (обычный участник команды) и `padmin/padmin` (платформенный админ) - часть интерфейса видна только админу, поэтому роли проверяются обоими. Чтобы не логиниться на каждом шаге, открывай сессию с постоянным профилем и сохраняй состояние:

  ```bash
  playwright-cli open http://localhost:5173/ --persistent
  # один раз пройти форму Keycloak, затем
  playwright-cli state-save .playwright-cli/auth-alice.json
  # в следующий раз
  playwright-cli state-load .playwright-cli/auth-alice.json
  ```

- **На стенде читаем и кликаем, данные не меняем без нужды.** Заказы, согласования и публикации уходят в настоящие Harbor, GitLab и Argo CD, подключённые к стенду.

## Тексты интерфейса (UX copy)

- **Все видимые пользователю тексты - продуктовые.** Ошибки, подсказки, описания полей, пустые состояния, тултипы и футеры пишутся для клиента: короткие законченные предложения, обращение к пользователю («Используйте...», «Укажите...»), без точек с запятой, без стиля спецификации и без жаргона (regex, «DNS-формат», названия внутренних сущностей). Перед сдачей перечитай текст глазами клиента: если похоже на вывод линтера или сгенерированный нейросетью текст - переписать.
- **Ошибки валидации инпутов - по единому шаблону.** Показываем одну ошибку - первую непройденную проверку, а не список. Канонические формулировки (новые проверки формулировать по этим же образцам):
  - обязательное поле: «Обязательное поле.»
  - допустимые символы: «Используйте строчные латинские буквы, цифры и дефис.»
  - граничные символы: «Первый и последний символ - буква или цифра.»
  - максимальная длина: «Не длиннее N символов.»
  - минимальная длина: «Не короче N символов.»
  - числовой диапазон: «Значение от N до M.»
  - занятое имя: «Имя «X» уже занято.»
- **О символах - только белым списком.** Сообщение перечисляет, что вводить можно («Используйте строчные латинские буквы, цифры и дефис.»), и никогда - что запрещено («спецсимволы недопустимы», «без пробелов»). Запрещённое следует из белого списка само.
- **Канонические тексты и валидаторы - в `web/src/form/fieldErrors.ts`** (`fieldMsg`, `dnsLabelError`, `withField`, `ruPlural`). Новые проверки строятся на этом модуле, свои строки не сочиняем.
- **`description` поля описывает формат заранее** - коротко и без глаголов: «Строчные латинские буквы, цифры и дефис.» Тогда ошибка не становится для пользователя сюрпризом.
- **Не дублировать текст ошибки поля в других местах.** Если поле уже подсвечено с текстом правила, баннер или соседний блок ссылается на поле коротко («Namespace указан неверно.») и не повторяет само правило.

## Конфигурация

- **Описание переменной пишется один раз на аудиторию.** `internal/config/config.go` - источник правды. У поля обязательны теги `env:` и `desc:"..."` (одно английское предложение о том, зачем переменная), плюс `example:"..."`, если дефолта нет. Если без переменной портал не стартует, это пишется в самом `env`-теге: `env:"HARBOR_URL,required,notEmpty"` - тогда `config.Load` сам откажется стартовать и назовёт все недостающие переменные разом. Отдельных проверок в `main.go` для этого заводить не нужно.
- **Корневой `.env.example` не правится руками - он генерируется.** После правки поля запусти `make env-example`; тест `TestEnvExampleGenerated` падает, пока файл в репозитории и теги расходятся. (`deployments/.env.example` - это не полный референс, а мелкий оверрайд для `make up-upstreams-infra`; его трогать не нужно.)
- **Русская подпись для страницы «Конфигурация» - в `web/src/pages/configText.ts`.** Там же, где остальной продуктовый текст, по правилам раздела «Тексты интерфейса». Тест `TestEveryVariableDocumented` требует строку для каждой переменной и падает на лишних.

## Наблюдаемость (логи и метрики)

- **Новая фича - сразу с логами и метриками, где это рационально.** Не «потом»: если фича меняет состояние, ходит во внешнюю систему, имеет фоновый цикл или измеримый исход (заказы, согласования, reconcile, вызовы апстримов) - покрой её структурным логом и, если это значимый сигнал, метрикой. Тривиальные чистые функции/хелперы и обработчики, уже покрытые HTTP-логом и метриками, отдельно инструментировать не нужно.
- **Логи - единый формат (см. `internal/observability/logger.go`).**
  - Каждая подсистема логирует через `observability.Component(log, "<subsystem>")`, чтобы в каждой строке был `component=` (api, provisioning, publications, poller, ...). Дочерний логгер прокидывается из `main` в сервис (поле `Log`).
  - Сообщение - короткое, в нижнем регистре, событийного стиля и **стабильное** (без подстановки значений): `"order transition"`, `"http request"`, `"reconcile ok"`. Переменные данные - только в атрибутах (так логи остаются grep-friendly).
  - Используй канонические ключи атрибутов из doc-комментария `logger.go` (`request_id`, `order_id`, `publication_id`, `chart`, `from`/`to`, `actor`, `reconciler`, `duration_ms`, `err`), не плоди синонимы. `request_id` - это HTTP-корреляция (chi), id заказа - это `order_id`.
  - Уровни: `Debug` - детальный поток (тики reconcile, переходы FSM, шумные эндпоинты `/health`/`/ready`/`/metrics`); `Info` - заметные бизнес-события; `Warn` - ожидаемые/восстановимые ошибки; `Error` - сбои, требующие внимания.
- **Метрики - префикс `console_`, конвенции Prometheus** (базовые единицы в секундах, суффикс `_total` у счётчиков), регистрация через `promauto` в `internal/observability/metrics.go`. Значимый сигнал отражай и на дашборде Grafana (`deployments/grafana/dashboards/console.json`).

## Журнал изменений (CHANGELOG)

- **Правила ведения журнала - в скилле `changelog`** (`.claude/skills/changelog`): формат Keep a Changelog, категории, стиль записей, выпуск версии. Скилл универсальный, здесь - только то, что специфично для этого проекта.
- **Файлы - `CHANGELOG.md` (английский) и `CHANGELOG.ru.md` (русский)**, оба правятся в одном изменении и должны совпадать по структуре: те же версии, даты, категории и порядок записей.
- **Запись добавляется в том же PR, что и само изменение**, в раздел `## [Unreleased]`. Не «потом перед релизом»: релиз собирается из накопленного `[Unreleased]`, а не восстанавливается по git log.
- **Что попадает в журнал:** всё значимое и видимое пользователю - новая возможность, изменённое поведение или формулировка, удаление, исправление дефекта, правка безопасности, новое требование к запуску или конфигурации. Рефакторинг, тесты, CI, обновления зависимостей без видимого эффекта и правки комментариев в журнал не идут.
- **Как пишем:** по-продуктовому, для клиента, как в разделе «Тексты интерфейса» выше. Одно законченное предложение на запись, без технических подробностей: без имён файлов, функций, пакетов, таблиц, флагов и эндпоинтов, без номеров задач и без скопированных заголовков коммитов. «Исправлены ошибки» и «улучшена производительность» - не записи.
- **Версию не проставляем сами.** `[Unreleased]` превращается в раздел `## [X.Y.Z] - ГГГГ-ММ-ДД` только в релизном PR (`release/vX.Y.Z`), из него же GitHub Action собирает тег и Release. Порядок - в скилле `git-workflow`.
