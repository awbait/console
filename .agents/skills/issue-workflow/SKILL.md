# Issue workflow

Задачи ведутся в issues. Issue - единственный контракт между человеком
и агентом: в нём постановка, план, решение по плану, ход работы и итог.
Агент не помнит прошлых разговоров, поэтому всё, что нужно следующему
исполнителю, записывается в issue.

Этот скилл описывает жизнь задачи: метки, статусы и кто что делает.
Ветки, коммиты, PR и итоговый комментарий о причине и проверке описаны
в скилле `git-workflow`. Где что хостится и как обращаться к API, там же,
в разделе «Forge». Правила проекта (`AGENTS.md`) старше этого скилла.

## Принципы

1. Issue самодостаточен: по нему одному понятно, что сделать и как проверить.
2. Состояние задачи - метки и комментарии. Отдельного трекера нет.
3. Один issue - одна ветка - один PR.
4. Одобрение плана и слияние PR делает только человек.
5. Агент не расширяет задачу: всё за пределами критериев приёмки - новый issue.

## Метки

Набор меток проекта лежит в файле меток репозитория и раскатывается
скриптом из `tools/` (в Console: `.github/labels.json` и
`tools/github_labels.py`, сначала с `--dry-run`). Ниже схема по умолчанию.

Метки с общей частью до `/` взаимоисключающие (scoped labels в Gitea):
при добавлении `status/ready` Gitea сам снимает прежний `status/*`.
В GitHub такой автоматики нет, там прежнюю метку снимают явно.

**Тип, ровно один:**

| Метка | Когда |
| --- | --- |
| `type/feature` | новая возможность |
| `type/bug` | ошибка |
| `type/enhancement` | улучшение существующего |
| `type/chore` | рефакторинг, зависимости, инфраструктура |
| `type/docs` | документация |
| `type/design` | продуктовые решения: как это должно работать и выглядеть, до кода |
| `type/research` | исследование без кода; результат - комментарий или документ |

**Статус, ровно один у открытой задачи:**

| Метка | Значение |
| --- | --- |
| `status/triage` | новая, не размечена |
| `status/needs-analysis` | нужен анализ и план перед работой |
| `status/needs-approval` | план готов, ждёт решения человека |
| `status/ready` | можно брать в работу |
| `status/in-progress` | взята, исполнитель указан в assignee и claim-комментарии |
| `status/review` | PR открыт или результат выложен, ждёт человека |
| `status/blocked` | стоит; причина в комментарии |

Закрытый issue - сделано, отдельной метки нет.

**Приоритет, необязательно:** `priority/p0` (блокер, бросаем всё),
`priority/p1` (в текущую сборку), `priority/p2` (когда дойдут руки;
по умолчанию, если метки нет).

**Область, если проект делит задачи по частям, ровно одна:** набор `area/*`
перечислен в файле меток (в Console: `area/backend`, `area/frontend`,
`area/charts`, `area/ops`, `area/security` и другие). Задача, которая
затрагивает и сервер, и клиент, делится на две: серверная часть с API и
клиентская с экранами; клиентская блокируется серверной (контракт API). Без
области остаются только организационные задачи. В репозитории с одной частью
метки области не нужны: область - сам репозиторий.

**Флаг:** `human-only` - задачу нельзя отдавать агенту: архитектура,
безопасность, решения владельца. По умолчанию любую задачу можно делегировать.

**Вехи.** Веха (milestone) - сборка или релиз, в который задача входит,
если проект планирует релизы вехами. Задача без вехи ещё не распределена.

## Жизненный цикл

```
создание -> triage -> [анализ -> одобрение] -> ready -> работа -> review -> закрытие
```

1. **Создание.** Автор заводит issue по шаблону. Метки из шаблона ставятся сами,
   статус `status/triage`.
2. **Разметка.** Проверить, что шаблон заполнен. Поставить `type/*`, при
   необходимости `priority/*` и веху. Дальше:
   - постановка полная и путь очевиден: `status/ready`;
   - нужно разобраться в коде или выбрать подход: `status/needs-analysis`;
   - не хватает сведений: комментарий, что именно нужно, статус остаётся.
3. **Анализ.** Прочитать issue, документы проекта и код. Написать план
   комментарием: что меняется, где, какие есть варианты и какой предлагается,
   что вне задачи, как проверить. Статус `status/needs-approval`. Дальше
   агент останавливается.
4. **Одобрение.** Человек отвечает в issue: принять (`status/ready`),
   поправить (анализ дорабатывается) или отменить (закрыть с причиной).
5. **Работа.** Claim, ветка и код по `git-workflow`, комментарии в issue
   на ключевых этапах.
6. **Review.** PR открыт с `Closes #N` (GitHub) или `fixes #N` (Gitea),
   итоговый комментарий в issue по `git-workflow`, статус `status/review`.
   Агент останавливается.
7. **Закрытие.** Человек сливает PR, issue закрывается сам по ключевому слову.
   Задачи без кода (`type/research`, часть `type/design` и `type/docs`)
   закрывает человек после того, как принял результат.

## Порядок действий агента

### Проверка перед началом

1. Метка `human-only`: отказаться и написать, что задача помечена human-only.
2. Статус соответствует действию: анализ берётся из `status/needs-analysis`,
   работа из `status/ready`. Другой статус - спросить пользователя.
3. Шаблон заполнен: есть контекст, что сделать и критерии приёмки.
   Нет - комментарий «не хватает: ...» и стоп.
4. Блокеры: «Блокируется: #M» в теле. Если #M открыт - комментарий и стоп.
5. Claim другого исполнителя: `status/in-progress` и чужой assignee - стоп.
   Свой - режим продолжения, см. ниже.

### Claim

Назначить себя (или пользователя, от чьего имени работает агент),
поставить `status/in-progress` и оставить комментарий:

```
Взял в работу. Ветка: feat/42-short-slug. Исполнитель: <агент или роль>.
```

Для анализа то же самое без ветки: «Начал анализ».

### Во время работы

- Комментарии только на ключевых этапах: «сервер готов, перехожу к клиенту».
  Не по каждому файлу.
- Коммитить после каждого законченного шага и не реже чем раз в полчаса
  работы: иначе после сбоя нечего продолжать.
- Новая находка вне задачи - отдельный issue со ссылкой, а не правка в этой
  ветке.

### Передача другому исполнителю

Статус обратно в `status/ready`, комментарий:

```
Передаю: <кому или какой роли>.

Сделано:
- ...
Состояние: ветка <ветка>, последний коммит <sha> "<сообщение>"; что работает, что нет.
Осталось:
- ...
Подводные камни:
- ...
```

Ветку и worktree не удалять: следующий исполнитель продолжит в них.

### Продолжение после сбоя

Если задача в `status/in-progress` на тебе:

1. Прочитать все комментарии с момента claim.
2. Найти ветку из claim-комментария, `git fetch` и перейти на неё.
3. `git log --oneline -20` и `git diff main...HEAD`: что уже сделано.
4. Комментарий «Продолжаю после <причина>, с шага <шаг>» и продолжить.

### Когда остановиться и спросить

Комментарий «Нужно решение: ...», статус `status/blocked` или прежний,
и стоп, если:

- непонятны критерии приёмки;
- есть несколько равноценных подходов;
- меняется контракт API между частями системы или схема данных;
- нужна новая зависимость или сервис;
- найдена серьёзная ошибка рядом, не относящаяся к задаче;
- тесты падают по неочевидной причине.

## Создание задачи

Когда пользователь просит завести задачу: issue по подходящему шаблону
(`.github/ISSUE_TEMPLATE/` на GitHub, `.gitea/issue_template/` в Gitea),
заполненные разделы, метки типа и статуса,
веха, если сборка понятна. Заголовок короткий и конкретный, язык - как
в остальных issue проекта.

## Запрещено

1. Брать задачи с `human-only`.
2. Сливать PR и закрывать issue вручную, кроме случая, когда пользователь
   прямо просит.
3. Менять метки на чужих задачах в `status/in-progress`.
4. Игнорировать блокеры.
5. Делать больше, чем требуют критерии приёмки.
6. Менять код через API хостинга (создание файлов через MCP или REST):
   изменения кода идут только через `git commit` в ветке.
