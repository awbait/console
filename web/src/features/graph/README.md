# Графы

Модуль отвечает за все графовые экраны портала: редактор сетевых политик и
read-only карты (event mesh, топология ресурсов), а также декларативный редактор
коллекций values.

## Структура

```
core/          домен-независимая часть: модель, канва, карточка, рёбра, стили
declarative/   настраиваемые коллекции узлов и связей, команды, формы и песочница
profiles/      конкретные домены
  policies/    интерактивный редактор: values <-> граф, состояние холста
  eventMesh/   read-only профиль knative + пример данных
  resources/   read-only профиль ресурсов namespace + пример данных
pages/         страницы: /policies-map, /graph/event-mesh, /graph/topology
environments.ts  список сред платформы (общий, не про политики)
```

`core/model.ts` описывает граф в нейтральных терминах: боксы (`GraphGroup`),
карточки (`GraphNode`) со строками (`GraphRow`) и стрелки (`GraphLink`). Профиль
(`GraphProfile`) добавляет к этому свой словарь: как называются виды узлов, какой
у них акцент, что написано в легенде и в пустом состоянии.

`core/GraphView.tsx` рисует такую модель и по умолчанию работает на просмотр.
Декларативный редактор включает `editable` и получает события выбора карточки,
связи, соединения точек и перемещения. Семантические команды остаются в редакторе.
Карточки, строки, стрелки и раскладка общие с `/graph/topology`.

Раскладку задаёт профиль (`layout`): боксы ставятся в ряд или в столбик, а карточки
внутри бокса - простым списком или колонками по стрелкам (точки входа слева, то,
куда они ведут, - правее). Топология ресурсов читается слева направо внутри
namespace, а сами namespace идут в столбик; event mesh идёт слева направо целиком,
потому что потребители обычно живут в соседних namespace.

## Редактирование values

`declarative/ValuesGraph.tsx` редактирует списки объектов через профиль
`declarative` версии 1. `model.ts` отделяет проекцию от команд изменения:
просмотр и раскладка не вызывают запись values. Ключ записи является непустой
строкой, индекс массива используется только для адресации текущего элемента.
Переименование обновляет ссылки, удаление узла с входящими или исходящими
связями запрещено. Параллельные связи имеют собственные ключи и не схлопываются.

Настройки задаются во вкладке «Граф» конструктора версии или в JSON. Редактор
использует `SchemaForm` для свойств, передавая исходную схему как `rootSchema`,
чтобы ссылки `$ref` продолжали разрешаться относительно всей схемы чарта.
Бэкенд проверяет описание при публикации, уникальность ключей и существование
концов связей при оформлении заказа, в том числе из YAML. Пустые графы разрешены.

Песочница: `cd web; bun run dev`, затем `/playground.html?graph`. Пример Event Mesh
условный, он не является контрактом реального чарта. В песочнице доступны
редактор настройки, граф, YAML, схема и JSON view-документа. Данные остаются
в localStorage браузера, запросов записи в портал нет.

На `/graph/topology` кнопка «Открыть в конструкторе» открывает локальную копию
примера ресурсов. Без входа тот же пример доступен по
`/playground.html?graph=topology`. Это адаптация демонстрационных данных к values,
а не Kubernetes-манифесты и не изменение ресурсов кластера.

В `nodes.<type>.display` можно задать `tone` (`neutral`, `accent`, `muted`, `warn`),
`subtitle` и `group` (пути внутри записи), `rows` (список `{id,label,field}`).
Путь `field` читается из объекта узла; одинаковые значения `group` объединяют
разные типы узлов. Строки имеют фиксированные ID, уникальные в пределах типа.
`relations.<type>.from.row` и `to.row` указывают ID строки соответствующего типа
узла. Без `row` стрелка подключается к заголовку карточки. Удаление используемой
строки делает маппинг невалидным до исправления связи. Строки не генерируются
из массивов портов автоматически. Настройки отображения values не меняют.

`groups.<type>` описывает области как отдельные коллекции (`collection`, `key`,
`label`, `title`, `form`). `accepts` задаёт разрешённые ID типов узлов; опциональный
`acceptsField` указывает массив дополнительных ограничений в конкретной записи
области. Отсутствующее поле не сужает `accepts`, пустой массив запрещает все типы.
Узел с `group: {type, field}` ссылается на ключ области указанного типа.
Такой узел не использует `display.group`. Без явных областей прежняя группировка
продолжает работать, `ungroupedTitle` меняет название общей рамки «Ресурсы».

Области доступны в конструкторе как «Типы областей». Клик по рамке открывает
форму её параметров; переименование ключа обновляет ссылки узлов, удаление
непустой области запрещено. ПКМ по узлу открывает «Переместить в…»; разрешения,
существование области, схема и заблокированные поля проверяются до записи.
Ошибка оставляет окно открытым. Прямая запись через YAML/API также проходит
серверную проверку принадлежности и разрешённых типов.

Перетаскивание расширяет родительскую рамку через `expandParent`, не меняя
принадлежность узла. Позиции и `groupSizes` сохраняются в `editor_state`.
Подписи связей рисуются поверх холста, компенсируют уменьшение масштаба;
параллельные связи получают разные смещения подписей.

В первой версии граф показывает только явно переданные values. Он не
материализует Helm defaults и не восстанавливает топологию из ресурсов кластера.
Неподдерживаемые варианты: словари сущностей, составные ключи, ссылка внутри
узла вместо отдельной коллекции связей, селекторы и вычисляемые связи.
Неизвестные поля исходных записей сохраняются. При повреждённых ссылках или
неуникальных ключах запись с холста блокируется до исправления values.
Раскладка хранится отдельно, с привязкой к версии чарта и описанию графа.
Конверт раскладки декларативного редактора имеет `version: 2`: позиции карточек
относительны группе. Прежняя плоская раскладка версии 1 не применяется, values
при переходе не меняются. Версия самого описания `graph` остаётся 1.

`profiles/policies/PoliciesGraph.tsx` - отдельный интерактивный редактор со своей
моделью (`topology.ts`): рисование стрелок, диалоги, контекстные меню, правила
валидности (отправителю нужен service account, получателю - exposed-порт). Он не
использует `core/GraphView`, но живёт в том же визуальном языке (`core/graph.css`) и
не знает про values: конвертация в обе стороны лежит в `valuesBuilder.ts` и
`valuesParser.ts`.

Граф владеет ровно четырьмя ключами записи `policies[]`: `selector`,
`serviceAccount`, `ingress`, `egress`. Всё остальное принадлежит тому, кто это
написал - другому режиму редактирования, руке пользователя, будущей версии чарта -
и переносится в новую запись как есть, включая имя и порядок ключей. Поэтому
`buildPolicies` принимает предыдущий `policies[]`: он не генерирует секцию заново,
а вписывает нарисованное в уже существующие записи. Незнакомое поле не может
исчезнуть от того, что пользователь провёл стрелку.

Обратная сторона: если две записи описывают один и тот же workload (одинаковый
`selector`), на холсте им соответствует одна карточка, и при записи обратно одна из
записей потерялась бы. Такие values разбор отклоняет с объяснением, а не сливает
молча.

## Маппинг полей: где он живёт

Профиль (домен) - это код: для политик «стрелка из namespace заказа становится
egress-правилом на источнике», «отправителю нужен service account», «правила одного
владельца сливаются в одну запись». Это поведение, и меняется оно редко.

Имена полей - это данные, и едут они вместе с версией чарта: блок `graph` в
view-документе версии (`internal/views/graph.go` валидирует, `mapping.ts` читает).
Причина простая: редактор не показывает values, он их переписывает, поэтому обязан
знать их точную форму. Зашей это знание в релиз консоли - следующая версия чарта
сломает граф всем заказам, оставшимся на старой. Положи в view-документ версии -
две версии одного чарта несут два маппинга, и оба работают.

Чарту, который называет поля по соглашению, достаточно:

```json
{ "views": { "order": { ... } }, "graph": { "profile": "policies" } }
```

Если чарт назвал поля иначе, они переименовываются там же:

```json
{
  "graph": {
    "profile": "policies",
    "entries": "/network/rules",
    "entry": { "selector": "podSelector", "ingress": "inbound" },
    "peer":  { "namespace": "ns" }
  }
}
```

Включение - это наличие валидного блока, а не отдельный флаг: булев переключатель
рядом с документом рано или поздно разойдётся с самим документом. `"enabled": false`
гасит редактор, не удаляя настройку. Нет блока, выключен, профиль неизвестен консоли -
вкладки «Граф» просто нет, форма и YAML работают как обычно.

Пути из блока проверяются по `values.schema.json` **этой же версии** при
редактировании и согласовании, поэтому несовпадение видит автор в конструкторе, а не
пользователь посреди заказа. Проверка следует общему правилу пакета `views`:
сообщается только то, что можно доказать, схема без описанной структуры не винится.

Реестр консоли ключуется id профиля, а не именем чарта
(`features/orders/valuesEditors.tsx`): консоль знает домены, а какой домен включить и
куда мапить поля, решает публикация.

## Состояние холста

Холст держит то, чего нет в values: workload без стрелок вместе с его service
account и портами, пустые namespace, позиции боксов. Схема чарта запрещает лишние
ключи, поэтому это хранится рядом с заказом - в колонке `requests.editor_state`
(см. `internal/store/migrations/000016_request_editor_state.sql`).

Формат - конверт `{ profile, version, chartVersion, data }`
(`profiles/policies/editorState.ts`). Профиль в конверте обязателен: чужой документ
или другой формат читаются как «сохранённого холста нет», и граф строится из одних
values, а не падает. `version` - формат самого конверта, `chartVersion` - версия
чарта, под которую холст рисовали.

Зачем нужен `chartVersion`: сохранённые воркоады возвращаются на values по
селектору, а что значит селектор - решает чарт. Поэтому холст переиспользуется
только на той же линии релиза (патч можно, минор нельзя - те же рассуждения, что и
у диапазона версий плагина). Потерять один раз расстановку боксов после обновления
чарта дешевле, чем прицепить сохранённый service account не к тому воркоаду. Холсты,
сохранённые до появления поля, читаются как раньше: другого маппинга, из которого
они могли бы взяться, никогда не существовало.

Правило записи: клиент, который не пользуется визуальным редактором (форма, YAML),
поле не отправляет - тогда бэкенд сохраняет то, что уже лежит. Явный `null` очищает.

## Источник данных

`profiles/policies/topology.ts` объявляет `TopologyProvider` (подсказки namespace,
готовая топология). Сейчас реализован только `manualProvider` - пользователь рисует
руками. Демо-профили ходят в захардкоженные примеры (`demoData.ts`); реальный
источник (коллектор или API кластера) подключается на их место.
