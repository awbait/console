# Конструктор формы заказа

В конструкторе вы задаёте, какие параметры заполняет заказчик и как он управляет уже заказанным сервисом. Для каждой версии чарта создайте свой документ `view.schema.json`.

Поля и ограничения берутся из `values.schema.json` чарта и его зависимостей. Документ версии выбирает поля для формы, меняет подписи, добавляет вкладки и действия. Он также задаёт автоматическое заполнение значений, источник имени сервиса и namespace.

Начните с небольшой формы. Проверьте её в предпросмотре, затем добавьте остальные возможности и отправьте версию на согласование. Порядок публикации описан на странице [Публикация сервиса](publishing).

## Откройте конструктор

На странице сервиса нажмите **Управление** и откройте нужную версию.

Слева находятся вкладки с документами:

| Вкладка | Для чего нужна |
|---|---|
| **view.schema.json** | Здесь вы пишете документ версии. |
| **values.schema.json** | Здесь можно посмотреть исходную схему чарта. Она доступна только для чтения. |
| **Зависимости** | Здесь показаны схемы зависимостей, их версии и пути к значениям. Вкладка появляется, если у чарта есть зависимости. |

Справа находятся **Форма заказа** и **Страница продукта**. Это два представления одного пробного заказа. Заполните форму, затем переключитесь на страницу продукта и проверьте вкладки, таблицы и меню **Действия**.

![Конструктор документа версии](images/view-constructor.png)

### Пользуйтесь подсказками

Нажмите **Ctrl+Space**, чтобы увидеть подходящие ключи и значения. Подсказки учитывают выбранную версию чарта и место, где вы пишете:

- В `include`, `exclude`, `required` и ключах `overrides` предлагаются поля формы.
- Для вложенных объектов предлагаются пути, например `tls/certificates`. Такой путь позволяет показать список без дополнительного заголовка объекта `tls`.
- В `items` предлагаются пути к спискам.
- В колонках таблицы предлагаются поля одной записи.
- В `form` и `actions.view` предлагаются формы из вашего документа.
- В `actions.in` предлагаются доступные места для действия.
- В `defaults` и `initial` предлагаются поля для заполнения и доступные ссылки на сведения о заказе.

Для имён полей подсказки показывают также один уровень вложенных объектов. Более глубокий путь можно написать вручную. Внутрь записей списка такие подсказки не заходят: настройте запись через `ui:view` или отдельную форму вкладки.

Если остаётся единственное продолжение, редактор показывает его серым текстом. Нажмите **Tab**, чтобы принять его.

Наведите указатель на ключ документа, чтобы прочитать пояснение. На вкладках схемы чарта и зависимостей наведите его на значение `$ref`: подсказка покажет, какое определение открывает ссылка. Нажмите **Ctrl+клик** или **F12**, чтобы перейти к определению внутри этой схемы. Переход к ссылкам на другие файлы не поддерживается.

![Схема чарта в конструкторе](images/view-chart-schema.png)

### Возьмите документ другой версии

Кнопка **Взять из версии** предлагает согласованные документы других версий этого же чарта. Она появляется, когда есть документ, который можно использовать.

Выберите версию. Если редактор уже содержит ваш документ, портал попросит подтвердить замену. Полученный текст станет черновиком текущей версии и будет проверен по её схеме.

> [!TIP]
> После переноса проверьте пути к полям. Между версиями чарт мог изменить названия, типы и вложенность. Согласование исходного документа не заменяет проверку новой версии.

### Сохраняйте черновик и отправляйте версию

Черновик сохраняется автоматически примерно через две секунды после остановки ввода. Его также можно сохранить кнопкой **Сохранить черновик**.

Ориентируйтесь на надпись рядом с кнопкой:

| Надпись | Что означает |
|---|---|
| **Черновик сохранится сам** | В редакторе есть изменения. |
| **Сохраняем…** | Портал сохраняет документ. |
| **Черновик сохранён** | Текущий текст сохранён. |
| **Не сохранено** | Исправьте JSON или ошибку сохранения. |

Незаконченный JSON не сохраняется. Портал также отклоняет документ с ошибками формата. При этом сохранённый черновик ещё может содержать неверные ссылки на поля чарта: перед согласованием нужна полная проверка.

Нажмите **Отправить на согласование**, когда под редактором нет ошибок и предпросмотр работает как ожидается. Портал сначала сохранит документ, затем отправит версию администратору.

Во время согласования документ доступен только для чтения. Кнопка **Отозвать для изменения** возвращает его в работу. Если вы меняете уже опубликованную версию, заказчики продолжают пользоваться последним согласованным документом до согласования новых правок.

## Начните с минимального документа

Обязателен только блок `views` с формой `order`:

```json
{
  "views": {
    "order": {}
  }
}
```

Такой документ показывает собственные поля чарта, кроме скрытых в его схеме. Поля зависимостей автоматически не добавляются.

Чтобы начать с пустой формы параметров, укажите пустой `include`:

```json
{
  "views": {
    "order": {
      "include": []
    }
  }
}
```

Общие поля заказа, например кластер и отображаемое имя, настраиваются отдельно от параметров чарта. Пустой `include` их не убирает.

![Минимальная форма заказа](images/view-minimal.png)

### Из чего состоит документ

| Ключ | Что задаёт |
|---|---|
| `views` | Формы заказа, редактирования параметров и отдельных записей. Форма `order` обязательна. |
| `tabs` | Вкладки со списками на странице заказанного сервиса. |
| `actions` | Формы, которые открываются из меню **Действия**. |
| `defaults` | Значения, которые портал записывает поверх данных формы при сохранении заказа. |
| `initial` | Начальные значения, которые заказчик может изменить. |
| `graph` | Режим **Граф** для сетевых политик. |
| `approval` | Возможность автоматически принять изменения заказа в Git. |
| `version` | Необязательное число или строка. Портал не использует это поле для выбора поведения. |
| `$comment` | Ваша текстовая заметка. На работу документа не влияет. |

`version` не задаёт версию чарта. Версия чарта уже выбрана на странице конструктора.

Заметки `$comment` можно писать на верхнем уровне документа, внутри формы, вложенного `ui:view`, блоков `graph` и `approval`. Используйте строку:

```json
{
  "$comment": "Форма для заказчиков сервиса.",
  "version": 1,
  "views": {
    "order": {
      "$comment": "Параметры добавим после проверки схемы.",
      "include": []
    }
  }
}
```

Обычные комментарии `//` и `/* */` в JSON не используйте.

> [!NOTE]
> Все примеры ниже являются самостоятельными документами. Они предполагают, что названные поля есть в схеме вашего чарта. Перед вставкой замените пути и имена на свои. Документ не создаёт новые поля в `values.schema.json`.

## Выберите поля формы

Каждая форма внутри `views` поддерживает `include`, `exclude`, `required` и `overrides`.

| Ключ | Как использовать |
|---|---|
| `include` | Перечислите поля в нужном порядке. Форма покажет только их. |
| `exclude` | Если `include` отсутствует, перечислите поля текущего уровня, которые нужно убрать. |
| `required` | Перечислите поля, которые форма дополнительно потребует заполнить. |
| `overrides` | Укажите настройки отображения отдельных полей. |

Если заданы и `include`, и `exclude`, портал использует `include`. Убирайте ненужное поле из этого списка.

Без `include` порядок берётся из `propertyOrder` схемы, а затем из порядка остальных полей.

`required` дополняет обязательность из схемы чарта. Он не отменяет её и не выводит поле в форму сам по себе. Убедитесь, что обязательное поле видно заказчику.

Например, покажите имя, число экземпляров и контакт:

```json
{
  "views": {
    "order": {
      "include": [
        "name",
        "replicas",
        "contacts/responsible"
      ],
      "required": [
        "contacts/responsible"
      ],
      "overrides": {
        "name": {
          "title": "Имя экземпляра"
        },
        "replicas": {
          "title": "Количество экземпляров"
        },
        "contacts/responsible": {
          "title": "Ответственный",
          "description": "Укажите человека, к которому можно обратиться по работе сервиса."
        }
      }
    }
  }
}
```

В `description` объясняйте назначение поля. Требования к длине, символам и числам портал показывает отдельно по схеме чарта.

### Настройте вложенные поля

Путь `contacts/responsible` выбирает одно поле внутри объекта. Начальный `/` здесь не нужен.

Если вы показываете объект целиком, настройте его поля через `ui:view`. Для объекта эта настройка описывает его содержимое. Для списка она описывает одну запись.

В примере форма показывает все собственные поля чарта, кроме `internal`. Внутри `contacts` она скрывает `technicalOwner`:

```json
{
  "views": {
    "order": {
      "exclude": [
        "internal"
      ],
      "overrides": {
        "contacts": {
          "title": "Контакты",
          "ui:view": {
            "exclude": [
              "technicalOwner"
            ],
            "required": [
              "responsible"
            ],
            "overrides": {
              "responsible": {
                "title": "Ответственный"
              }
            }
          }
        }
      }
    }
  }
}
```

Настройки относятся к тому уровню, который рисует форма. Если в `include` указано `contacts`, настройку поля `responsible` поместите в его `ui:view`. Если указано `contacts/responsible`, используйте этот же путь в `overrides`.

Аналогично, чтобы убрать одно поле из видимого объекта, задайте `exclude` внутри его `ui:view`. Путь в верхнем `exclude` не вырезает поле из содержимого объекта.

### Выберите способ отображения

| Настройка | Результат |
|---|---|
| `title` | Заменяет подпись поля. |
| `description` | Заменяет пояснение под полем. |
| `"ui:widget": "edit"` | Использует обычное редактирование по типу поля. Может заменить `hidden`, заданный непосредственно у поля в схеме. |
| `"ui:widget": "hidden"` | Скрывает поле. |
| `"ui:widget": "single"` | Показывает первый элемент списка одной формой без кнопок добавления и удаления. |
| `"ui:readOnly": true` | Позволяет заполнить поле при создании, затем блокирует его при редактировании и обновлении версии. |
| `"ui:readOnly": false` | Снимает эту настройку у поля. Блокировка всего родительского объекта продолжает действовать. |
| `ui:view` | Настраивает поля объекта или одной записи списка. |
| `ui:uniqueBy` | Указывает поле записи, значения которого не должны повторяться в списке. |

Для объекта или списка `ui:readOnly` блокирует и вложенные поля.

Используйте `single`, только если заказ действительно содержит один элемент. Значение остаётся списком, а форма работает с элементом `0`. Настройка не добавляет ограничение на размер списка в схему чарта.

Например, один шлюз можно показать одной карточкой:

```json
{
  "views": {
    "order": {
      "include": [
        "gateways"
      ],
      "overrides": {
        "gateways": {
          "title": "Шлюз",
          "ui:widget": "single",
          "ui:view": {
            "include": [
              "name",
              "hostname",
              "enabled",
              "internalTag"
            ],
            "required": [
              "name"
            ],
            "overrides": {
              "name": {
                "title": "Имя шлюза",
                "ui:readOnly": true
              },
              "hostname": {
                "title": "Домен",
                "ui:widget": "edit"
              },
              "enabled": {
                "title": "Включён"
              },
              "internalTag": {
                "ui:widget": "hidden"
              }
            }
          }
        }
      }
    }
  }
}
```

Скрытие поля не заполняет его и не отменяет проверку схемы чарта. Для автоматической записи значения используйте `defaults`.

### Что форма берёт из схемы чарта

Не нужно заново описывать каждое поле в документе версии.

| Описание поля в схеме | Что увидит заказчик |
|---|---|
| `string` | Текстовое поле. |
| `integer` или `number` | Числовое поле. |
| `boolean` | Флажок. |
| `enum` | Выбор из списка. |
| `enumNames` рядом с `enum` | Понятные подписи вариантов вместо их значений. |
| Объект с `properties` | Группу вложенных полей. |
| `array` | Список с добавлением и удалением записей. |
| Объект с описанным `additionalProperties` | Набор пар «ключ и значение». |
| `oneOf` | Выбор варианта формы. |
| `default` и `const` | Предусмотренные схемой значения. |
| `defaultSnippets` для списка | Начальное содержимое добавляемой записи из первого примера. |

Форма учитывает обязательные поля и скрытие из подходящих условий `if`/`then`. Окончательную проверку значений выполняет схема чарта.

Дополнительные подсказки схемы можно передать через `overrides`. Например, задать подписи вариантов:

```json
{
  "views": {
    "order": {
      "include": [
        "mode"
      ],
      "overrides": {
        "mode": {
          "title": "Режим работы",
          "enum": [
            "shared",
            "dedicated"
          ],
          "enumNames": [
            "Общий",
            "Выделенный"
          ],
          "default": "shared"
        }
      }
    }
  }
}
```

В этом примере чарт должен принимать значения `shared` и `dedicated`. Настройки формы не меняют исходные ограничения чарта.

## Добавьте поля зависимостей

Портал собирает поля основного чарта и его зависимостей в общую схему для формы и проверки заказа.

Значения зависимости находятся под её `alias` из `Chart.yaml`. Если `alias` не задан, используется имя зависимости. Нужный ключ показан на вкладке **Зависимости**.

Например, чарт зависимости называется `pgbouncer`, а её `alias` равен `pooler`. Поле режима будет называться `pooler/poolMode`:

```json
{
  "views": {
    "order": {
      "include": [
        "name",
        "pooler/poolMode",
        "pooler/replicaCount"
      ],
      "required": [
        "pooler/poolMode"
      ],
      "overrides": {
        "pooler/poolMode": {
          "title": "Режим пула"
        },
        "pooler/replicaCount": {
          "title": "Количество экземпляров пула"
        }
      }
    }
  }
}
```

Для зависимости внутри другой зависимости путь продолжается, например `waypointNamespace/waypoint/waypoints`.

Учитывайте несколько правил:

- Поля зависимостей попадают в форму только через явный `include`.
- Можно выбрать отдельное поле или весь объект зависимости.
- Если основной чарт уже описывает объект зависимости, его настройки имеют приоритет при совпадении ключей. Зависимость дополняет отсутствующие настройки.
- Если у зависимости нет `values.schema.json`, портал не может построить её поля.
- Поле `global` зависимости не добавляется под её ключ. Общие значения задаются на уровне основного чарта.
- Если схема основного чарта запрещает дополнительные поля и не описывает ключ зависимости, исправьте схему чарта. Документ формы не устраняет эту ошибку.

## Различайте имена полей и указатели

В документе встречаются три вида путей.

| Где используется | Пример | Откуда считается путь |
|---|---|---|
| `include`, `required`, ключи `overrides` | `tls/certificates` | От объекта, который описывает текущая форма. |
| `identity`, `namespace`, ключи `defaults` и `initial`, `tabs.items` | `/gateways/0/name` | От корня значений заказа. |
| `ui:table.path` | `parentRefs/*/sectionName` | От одной записи таблицы. |

Путь с начальным `/` называется JSON pointer. Число в таком пути обозначает индекс списка, начиная с нуля. Например, `/gateways/0/listeners` указывает на список подключений первого шлюза.

У `enums.at` и `lookup.keys` тоже есть начальный `/`, но они считаются от одной записи вкладки. Источники `enums.from` и `lookup.in` считаются от всех значений заказа.

Знак `*` используется для сбора значений в колонках таблицы и `lookup.keys`. Он не заменяет индекс в `identity`, `defaults` или `tabs.items`.

## Задайте имя сервиса и namespace

Эти настройки работают в `views.order`. Внутри вложенного `ui:view` они недопустимы.

### Имя из параметров чарта: `identity`

Если чарт уже содержит поле имени экземпляра, укажите путь к нему:

```json
{
  "views": {
    "order": {
      "identity": "/gateways/0/name",
      "include": [
        "gateways"
      ],
      "overrides": {
        "gateways": {
          "ui:widget": "single",
          "ui:view": {
            "include": [
              "name"
            ],
            "required": [
              "name"
            ],
            "overrides": {
              "name": {
                "title": "Имя шлюза",
                "ui:readOnly": true
              }
            }
          }
        }
      }
    }
  }
}
```

Отдельное поле **Service name** исчезнет. Портал возьмёт имя из указанного поля и покажет его в сведениях о заказе.

По этому значению портал также проверяет совпадения имён между активными заказами одного чарта в одном кластере и namespace. Проверка `identity` относится к разным заказам. Для повторов внутри одного списка используйте `ui:uniqueBy`.

Без `identity` заказчик заполняет **Service name** отдельно.

### Namespace из общего поля заказа

Если `namespace` не задан, используется поле **Namespace** в форме заказа. То же поведение можно указать явно:

```json
{
  "views": {
    "order": {
      "namespace": {
        "source": "field"
      }
    }
  }
}
```

`source` по умолчанию равен `field`.

### Скопируйте namespace в параметры чарта

Строковое значение `namespace` задаёт поле, куда портал скопирует namespace заказа:

```json
{
  "views": {
    "order": {
      "namespace": "/namespace/namespaceName",
      "include": [
        "namespace"
      ],
      "overrides": {
        "namespace": {
          "ui:view": {
            "exclude": [
              "namespaceName"
            ]
          }
        }
      }
    }
  }
}
```

Заказчик вводит namespace в общем поле **Namespace**. Портал записывает его в `/namespace/namespaceName`, заменяя прежнее значение этого параметра.

### Возьмите namespace из параметров чарта

Для обратного направления используйте объект с `source: "values"`:

```json
{
  "views": {
    "order": {
      "namespace": {
        "source": "values",
        "pointer": "/namespace/namespaceName",
        "hideOrderField": true
      },
      "include": [
        "namespace/namespaceName"
      ],
      "required": [
        "namespace/namespaceName"
      ],
      "overrides": {
        "namespace/namespaceName": {
          "title": "Namespace сервиса"
        }
      }
    }
  }
}
```

Здесь заказчик заполняет параметр чарта. Из него портал получает namespace назначения.

`pointer` обязателен при `source: "values"`. Чтобы скрыть отдельное поле **Namespace**, явно укажите `hideOrderField: true`. Без этой настройки поле остаётся видимым, хотя источником namespace служит значение из `pointer`.

### Используйте постоянный namespace

```json
{
  "views": {
    "order": {
      "namespace": {
        "source": "fixed",
        "value": "shared-services",
        "hideOrderField": true
      }
    }
  }
}
```

При `source: "fixed"` обязательно поле `value`. Укажите имя длиной до 63 символов из строчных латинских букв, цифр и дефиса. Первый и последний символ должны быть буквой или цифрой. Имя целиком из цифр не принимается при заказе.

`hideOrderField` скрывает поле только для источников `values` и `fixed`. Для `field` оно остаётся видимым.

Объектная настройка `namespace` выбирает namespace назначения. Она не копирует его в параметры чарта. Если выбранный источник возвращает пустое значение, при сохранении портал использует имя сервиса.

## Заполните значения автоматически

Для автоматического заполнения есть два блока. Выбирайте их по тому, должен ли заказчик менять значение.

| | `initial` | `defaults` |
|---|---|---|
| Когда применяется | При открытии нового заказа и обновлении на новую версию. | При сохранении нового или изменённого заказа. |
| Может ли заказчик изменить значение | Да. | Введённое значение будет заменено. |
| Что происходит с уже заданным значением | Сохраняется. | Перезаписывается. |
| Подходящий пример | Ответственный или рекомендуемый размер. | Источник заказа, команда, обязательная служебная отметка. |

В обоих блоках ключом служит указатель на параметр чарта. Значением может быть строка, число, `true`, `false` или `null`. Объекты и списки здесь не задаются.

### Начальное заполнение: `initial`

```json
{
  "views": {
    "order": {
      "include": [
        "contacts/responsible",
        "replicas",
        "monitoring/enabled"
      ]
    }
  },
  "initial": {
    "/contacts/responsible": "{{.User.Name}}",
    "/replicas": 2,
    "/monitoring/enabled": true
  }
}
```

Форма откроется с заполненными значениями. Заказчик сможет их изменить.

При обновлении на новую версию портал берёт её `initial` и добавляет только отсутствующие поля. Значения, которые уже есть в заказе, сохраняются. При обычном редактировании без смены версии `initial` не применяется повторно.

### Обязательная запись: `defaults`

```json
{
  "views": {
    "order": {
      "include": [
        "name",
        "contacts/responsible"
      ]
    }
  },
  "defaults": {
    "/metadata/creator": "console",
    "/metadata/team": "{{.Team}}",
    "/metadata/author": "{{.User.Name}}",
    "/metadata/authorId": "{{.User.Subject}}",
    "/metadata/chart": "{{.Chart}}",
    "/metadata/chartVersion": "{{.ChartVersion}}",
    "/metadata/service": "{{.ServiceName}}",
    "/metadata/namespace": "{{.Namespace}}",
    "/metadata/cluster": "{{.Cluster}}",
    "/metadata/externalId": null
  }
}
```

Поля из `defaults` обычно не включают в форму. Если заказчик их изменит через другое представление, при сохранении портал всё равно запишет значения из документа.

Сведения об авторе в `defaults` относятся к автору заказа. Они не меняются на данные сотрудника, который позже редактирует чужой заказ.

### Какие сведения можно подставить

Пишите ссылку внутри строки, например `"{{.Team}}"`.

| Ссылка | Значение | В `initial` |
|---|---|---|
| `{{.Team}}` | Команда, от имени которой сделан заказ. | Да |
| `{{.ServiceName}}` | Имя сервиса в заказе. | Нет |
| `{{.Namespace}}` | Namespace назначения. | Нет |
| `{{.Cluster}}` | Кластер назначения. | Нет |
| `{{.Chart}}` | Имя чарта. | Да |
| `{{.ChartVersion}}` | Версия чарта. | Да |
| `{{.User.Name}}` | ФИО автора заказа. При начальном заполнении формы используются данные открывшего её пользователя. | Да |
| `{{.User.Subject}}` | Идентификатор пользователя в системе входа. | Да |
| `{{.Vars.OPS_DOMAIN}}` | Значение переменной платформы `OPS_DOMAIN`. | Да |

Переменные платформы создаёт администратор в разделе **Переменные**. В подсказках редактора доступны существующие переменные.

В `initial` нельзя использовать имя сервиса, namespace и кластер: при открытии формы они ещё не выбраны.

Ссылку можно соединить с текстом, например `"{{.ServiceName}}.{{.Vars.OPS_DOMAIN}}"`. Условия, функции и вычисления внутри ссылки не поддерживаются.

Портал обрабатывает выражения, которые начинаются с `{{.`. Шаблоны другого вида, например `{{ $labels.instance }}`, оставляет как текст.

### Сохраняйте нужный тип значения

Строка после подстановки преобразуется к типу поля из `values.schema.json`:

| Тип поля | Результат |
|---|---|
| `integer` | Целое число. |
| `number` | Число. |
| `boolean` | Логическое значение. Используйте `true` или `false`. |
| `string` | Строка. |

Например, если переменная `SERVICE_PORT` содержит `8080`, поле типа `integer` получит число `8080`, а не строку:

```json
{
  "views": {
    "order": {
      "include": [
        "name",
        "replicas"
      ]
    }
  },
  "initial": {
    "/replicas": "2"
  },
  "defaults": {
    "/service/port": "{{.Vars.SERVICE_PORT}}",
    "/service/enabled": "true",
    "/service/weight": "0.5",
    "/service/hostname": "{{.ServiceName}}.{{.Vars.OPS_DOMAIN}}"
  }
}
```

Для этого примера поля `port`, `enabled` и `weight` должны иметь типы `integer`, `boolean` и `number`. Переменные должны существовать в портале.

Правило преобразования одинаково для `defaults` и `initial`. Числа, логические значения и `null`, записанные непосредственно в JSON, передаются как есть.

Если схема не задаёт однозначный тип, строка остаётся строкой. Превратить строковый шаблон в объект или список нельзя.

Конструктор проверяет известные значения заранее. Например, ссылку на команду нельзя использовать вместо числа. Значение переменной платформы также должно подходить полю. Если ссылка находится внутри дополнительного текста, результат считается текстом.

### Указатели на элементы списка

`defaults` может заполнить поле существующей записи:

```json
{
  "views": {
    "order": {
      "include": [
        "gateways"
      ],
      "overrides": {
        "gateways": {
          "ui:widget": "single",
          "ui:view": {
            "include": [
              "name"
            ]
          }
        }
      }
    }
  },
  "defaults": {
    "/gateways/0/ipAddress": "{{.Vars.GATEWAY_IP}}"
  }
}
```

Такой указатель работает, если первый шлюз уже есть в значениях заказа. Портал может создать промежуточный объект, но не добавляет записи списка ради `defaults`. Если индекс отсутствует, запись по этому пути пропускается.

`initial` собирается до заполнения формы из пустого набора значений. Поэтому он не создаёт списки и не заполняет их отсутствующие элементы по индексу. Начальные значения полей новой записи списка задавайте в схеме чарта.

## Добавьте вкладки со списками

Блок `tabs` создаёт вкладки на странице заказанного сервиса. Каждая вкладка связана с одним списком значений и формой одной записи.

| Ключ вкладки | Что указать |
|---|---|
| `id` | Уникальное непустое имя вкладки. Имена `info`, `history` и `order` заняты. |
| `title` | Заголовок. Если его нет, показывается `id`. |
| `items` | Указатель на список во всех значениях заказа. |
| `form` | Имя формы из `views`, которая редактирует одну запись. |
| `addLabel` | Текст добавления записи в меню **Действия**. По умолчанию используется «Добавить» и заголовок вкладки. |
| `ui:table` | Колонки таблицы в нужном порядке. |
| `ui:uniqueBy` | Поле записи, которое должно быть уникальным в этом списке. |
| `enums` | Правила заполнения вариантов выбора из других списков заказа. |

Обязательны `id`, `items` и `form`. Форму `order` использовать как форму записи нельзя.

Порядок вкладок совпадает с порядком элементов `tabs`. Добавление открывает указанную форму. Редактирование и удаление доступны у строки таблицы. Портал учитывает минимальное число записей из схемы чарта.

Например, выведите подключения первого шлюза:

```json
{
  "views": {
    "order": {
      "include": [
        "gateways"
      ]
    },
    "listener": {
      "include": [
        "name",
        "port",
        "hostname"
      ],
      "required": [
        "name",
        "port"
      ],
      "overrides": {
        "name": {
          "title": "Имя подключения"
        },
        "port": {
          "title": "Порт"
        },
        "hostname": {
          "title": "Домен"
        }
      }
    }
  },
  "tabs": [
    {
      "id": "listeners",
      "title": "Подключения",
      "items": "/gateways/0/listeners",
      "form": "listener",
      "addLabel": "Добавить подключение",
      "ui:uniqueBy": "name",
      "ui:table": [
        {
          "path": "name",
          "label": "Имя"
        },
        {
          "path": "port",
          "label": "Порт"
        },
        {
          "path": "hostname",
          "label": "Домен"
        }
      ]
    }
  ]
}
```

Поля формы `listener` считаются от одной записи списка. Поэтому здесь нужно `name`, а не `gateways/0/listeners/name`.

> [!NOTE]
> Без `ui:table` вкладка не показывает записи таблицей. Меню добавления и назначенные действия остаются доступны, а вместо таблицы появляется «Здесь пока нечего показать.».

### Покажите вложенные значения в колонках

У обычной колонки задайте `path`. `label` необязателен: без него заголовком станет путь.

| Путь | Что попадёт в колонку |
|---|---|
| `name` | Поле записи. |
| `backend/port` | Поле вложенного объекта. |
| `parentRefs/0/sectionName` | Поле первого элемента вложенного списка. |
| `parentRefs/*/sectionName` | Значения поля из всех элементов списка. |
| `selector/*key` | Ключи набора пар. |
| `selector/*val` | Значения набора пар. |
| `selector/*/weight` | Поле `weight` каждого объекта в наборе пар. |
| `selector/*val/0` | Первое значение из собранного списка значений. |

`*` и `*val` перебирают элементы списка или значения объекта. `*key` собирает ключи объекта. Число сразу после перебора выбирает элемент из уже собранного результата.

Пример вкладки с метками:

```json
{
  "views": {
    "order": {
      "include": [
        "services"
      ]
    },
    "service": {
      "include": [
        "name",
        "selector"
      ]
    }
  },
  "tabs": [
    {
      "id": "services",
      "title": "Сервисы",
      "items": "/services",
      "form": "service",
      "ui:table": [
        {
          "path": "name",
          "label": "Имя"
        },
        {
          "path": "selector/*key",
          "label": "Метки"
        },
        {
          "path": "selector/*val",
          "label": "Значения"
        },
        {
          "path": "selector/*val/0",
          "label": "Первое значение"
        }
      ]
    }
  ]
}
```

При сборе через `*` повторяющиеся значения убираются. Несколько значений показываются через запятую. Объект выводится как пары «ключ: значение», а пустая ячейка обозначается дефисом.

### Получите значение из другого списка: `lookup`

Вычисляемая колонка может найти связанные записи и показать их поле.

| Ключ `lookup` | Назначение |
|---|---|
| `keys` | Указатель на ключи внутри текущей записи. Допускает перебор через `*`. |
| `in` | Указатель на список во всех значениях заказа. |
| `match` | Имя поля записи источника, которое сравнивается с ключом. |
| `get` | Имя поля записи источника, которое нужно показать. |

Все четыре ключа обязательны. `match` и `get` задают непосредственные имена полей источника.

Например, маршрут хранит имена подключений, а в таблице нужно показать их домены:

```json
{
  "views": {
    "order": {
      "include": [
        "gateways"
      ]
    },
    "route": {
      "include": [
        "name",
        "parentRefs"
      ]
    }
  },
  "tabs": [
    {
      "id": "routes",
      "title": "Маршруты",
      "items": "/routes",
      "form": "route",
      "ui:table": [
        {
          "path": "name",
          "label": "Имя"
        },
        {
          "path": "parentRefs/*/sectionName",
          "label": "Подключения"
        },
        {
          "label": "Домены",
          "lookup": {
            "keys": "/parentRefs/*/sectionName",
            "in": "/gateways/0/listeners",
            "match": "name",
            "get": "hostname"
          }
        }
      ]
    }
  ]
}
```

Для колонки с `lookup` обязательно задайте `label`. Обычный `path` ей не нужен. Ненайденные и пустые значения пропускаются, повторы убираются.

### Заполните варианты выбора: `enums`

`enums` превращает поле формы записи в выбор из значений другого списка заказа.

| Ключ правила | Назначение |
|---|---|
| `at` | Указатель на поле внутри редактируемой записи. |
| `from` | Указатель на список во всех значениях заказа. |
| `value` | Непосредственное имя поля записи источника, которое станет вариантом выбора. |

Все три ключа обязательны.

В этом примере поле `sectionName` предлагает имена существующих подключений:

```json
{
  "views": {
    "order": {
      "include": [
        "gateways"
      ]
    },
    "route": {
      "include": [
        "name",
        "parentRefs"
      ]
    }
  },
  "tabs": [
    {
      "id": "routes",
      "title": "Маршруты",
      "items": "/routes",
      "form": "route",
      "ui:table": [
        {
          "path": "name",
          "label": "Имя"
        }
      ],
      "enums": [
        {
          "at": "/parentRefs/0/sectionName",
          "from": "/gateways/0/listeners",
          "value": "name"
        }
      ]
    }
  ]
}
```

Числовой сегмент в `at` ведёт к схеме элемента списка. Поэтому варианты получат поля `sectionName` всех записей `parentRefs`, а не только первой.

Пустые и повторяющиеся варианты убираются. Если источник отсутствует или не даёт ни одного значения, исходные настройки поля остаются прежними.

## Запретите повторяющиеся имена записей

Добавьте `ui:uniqueBy`, если чарт использует поле записи как имя создаваемого ресурса.

Для списка на форме настройка находится в `overrides`:

```json
{
  "views": {
    "order": {
      "include": [
        "tls/certificates"
      ],
      "overrides": {
        "tls/certificates": {
          "title": "Сертификаты",
          "ui:uniqueBy": "name",
          "ui:view": {
            "include": [
              "name",
              "secretName"
            ],
            "required": [
              "name"
            ]
          }
        }
      }
    }
  }
}
```

Для списка на странице сервиса задайте `ui:uniqueBy` непосредственно у вкладки, рядом с `items`. Такой пример есть в разделе про подключения.

Укажите непосредственное имя строкового поля записи, например `name`. Проверка сравнивает непустые строки с учётом регистра. Обязательность имени задайте отдельно в схеме или форме.

При редактировании запись не сравнивается сама с собой. Если имя совпало с другой записью, поле покажет ошибку. При сохранении портал также проверяет правила из вкладок и верхних `overrides` всех форм. Поэтому правило действует и на значения, поступившие через YAML или импорт.

Для вложенного списка, который нужно проверять при сохранении заказа, объявите правило на вкладке с полным `items` либо в верхнем `overrides` формы с путём через объекты. Не оставляйте его только внутри вложенного `ui:view`.

## Добавьте формы в меню «Действия»

Форма внутри `views` сама по себе не создаёт пункт меню. Разместите её через `actions`.

| Ключ действия | Назначение |
|---|---|
| `view` | Имя формы из `views`. |
| `in` | `info` для вкладки общей информации или `tab:<id>` для вашей вкладки. |
| `label` | Текст пункта меню. Без него показывается «Редактировать» и имя формы. |

`view` и `in` обязательны. Форму `order` нельзя размещать в **Действиях**.

```json
{
  "views": {
    "order": {
      "include": [
        "name",
        "contacts"
      ]
    },
    "contacts": {
      "include": [
        "contacts"
      ]
    },
    "routing": {
      "include": [
        "routing"
      ]
    },
    "route": {
      "include": [
        "name"
      ]
    }
  },
  "tabs": [
    {
      "id": "routes",
      "title": "Маршруты",
      "items": "/routes",
      "form": "route",
      "ui:table": [
        {
          "path": "name",
          "label": "Имя"
        }
      ]
    }
  ],
  "actions": [
    {
      "view": "contacts",
      "in": "info",
      "label": "Изменить контакты"
    },
    {
      "view": "routing",
      "in": "tab:routes",
      "label": "Настроить маршрутизацию"
    }
  ]
}
```

Форма действия работает со всеми значениями заказа и показывает выбранные вами поля. Даже действие на вкладке не становится формой одной строки.

Для формы записи и формы действия используйте разные имена, если они описывают разные уровни значений.

## Включите режим «Граф»

Блок `graph` добавляет режим **Граф** рядом с формой и YAML. Сейчас поддерживается профиль `policies` для сетевых политик.

Если поля чарта соответствуют обычным названиям профиля, достаточно такого документа:

```json
{
  "views": {
    "order": {
      "include": [
        "policies"
      ]
    }
  },
  "graph": {
    "profile": "policies"
  }
}
```

По умолчанию редактор работает со списком `/policies`. Он читает и изменяет значения заказа.

![Режим графа](images/view-graph.png)

### Сопоставьте поля своего чарта

| Ключ | Что настраивает |
|---|---|
| `profile` | Профиль редактора. Обязательное значение: `policies`. |
| `enabled` | Включение редактора. По умолчанию включён. |
| `entries` | Указатель на список записей. По умолчанию `/policies`. |
| `entry` | Имена полей одной политики. |
| `rule` | Имена полей входящего или исходящего правила. |
| `peer` | Имена полей другой стороны соединения. |

В группах слева пишется имя поля профиля, справа имя поля вашего чарта:

| Группа | Поля профиля |
|---|---|
| `entry` | `name`, `enabled`, `selector`, `serviceAccount`, `ingress`, `egress` |
| `rule` | `ports`, `from`, `to` |
| `peer` | `namespace`, `selector`, `serviceAccount` |

Если поле не переименовано, используется его исходное имя. Внутри этих групп указывайте одно имя поля, а не путь через `/`.

Пример для чарта с другими названиями:

```json
{
  "views": {
    "order": {
      "include": [
        "network/rules"
      ]
    }
  },
  "graph": {
    "$comment": "Названия полей этой версии чарта.",
    "profile": "policies",
    "enabled": true,
    "entries": "/network/rules",
    "entry": {
      "name": "name",
      "enabled": "active",
      "selector": "podSelector",
      "serviceAccount": "account",
      "ingress": "incoming",
      "egress": "outgoing"
    },
    "rule": {
      "ports": "ports",
      "from": "sources",
      "to": "destinations"
    },
    "peer": {
      "namespace": "namespace",
      "selector": "podSelector",
      "serviceAccount": "account"
    }
  }
}
```

Список записей должен содержать входящие и исходящие правила. Входящее правило использует `from`, исходящее использует `to`. Поле `serviceAccount` другой стороны требуется для отправителя во входящем правиле.

Сопоставление меняет только названия полей. Оно не превращает произвольную структуру чарта в сетевые политики. Конструктор проверяет, что указанные поля существуют в схеме.

Чтобы отключить граф для версии, задайте `enabled: false`:

```json
{
  "views": {
    "order": {
      "include": [
        "policies"
      ]
    }
  },
  "graph": {
    "profile": "policies",
    "enabled": false
  }
}
```

Отключённый блок всё равно должен быть корректным. Если настройка больше не нужна, можно удалить весь `graph`.

При включённом графе заказ должен содержать хотя бы одно входящее или исходящее правило. Иначе портал попросит добавить связь. Работа с сетевыми политиками описана на странице [Сетевые политики](policy).

## Настройте принятие изменений заказа

`approval.autoMerge` управляет автоматическим принятием изменений заказа в Git. Это отдельная настройка от согласования самого документа версии.

Чтобы каждое изменение потребовало участия человека, укажите `false`:

```json
{
  "views": {
    "order": {}
  },
  "approval": {
    "$comment": "Изменения проверяет человек.",
    "autoMerge": false
  }
}
```

Чтобы разрешить автоматическое принятие в пределах настроек платформы, укажите `true`:

```json
{
  "views": {
    "order": {}
  },
  "approval": {
    "autoMerge": true
  }
}
```

Без `autoMerge` действует настройка установки портала. Значение `true` не включает автоматическое принятие, если администратор запретил его для всей платформы.

## Проверьте документ

Под редактором появляются ошибки с путями, например `/views/order/include/0`. Это место в документе версии, которое нужно исправить. В самом сообщении может быть другой путь: поле значений чарта, на которое вы сослались.

![Ошибки документа](images/view-errors.png)

Проверка проходит в несколько этапов:

1. Редактор проверяет синтаксис JSON.
2. Портал проверяет ключи, типы значений, формы, вкладки, действия и шаблоны.
3. Портал сверяет пути с доступной схемой чарта и зависимостей.
4. При сохранении заказа его значения отдельно проверяются по схеме чарта.

Надпись **Документ валиден** означает, что проверка документа не нашла ошибок. Она не подтверждает, что любой набор значений успешно развернётся.

Если часть схемы не описана достаточно подробно, портал не всегда может доказать, что путь неверен. Поэтому проверяйте и документ, и заполненную форму.

### Что проверить в предпросмотре

- Поля идут в нужном порядке и имеют понятные подписи.
- Видны все обязательные поля.
- Вложенные объекты и списки открываются правильно.
- Новую запись можно добавить, изменить и удалить.
- Повтор имени в списке отклоняется.
- Колонки показывают нужные значения.
- `lookup` находит связанные записи.
- `enums` предлагает значения из заполненного источника.
- Меню **Действия** открывает нужные формы.
- Имя сервиса и namespace берутся из ожидаемых полей.

Данные предпросмотра не создают реальный заказ. Изменения на странице продукта остаются в предпросмотре.

Предпросмотр не выполняет подстановки `initial` и `defaults`. Их итоговые значения проверьте на форме реального заказа и при его сохранении после публикации версии.

## Напишите документ с помощью нейросети

Над этой страницей находятся кнопки **Скачать промт** и **Скопировать промт**. Они дают один и тот же готовый запрос для подготовки документа.

1. Скопируйте промт в чат с нейросетью или скачайте его.
2. Передайте `values.schema.json` нужной версии.
3. Если используются зависимости, передайте их схемы и сведения из `Chart.yaml`, включая `alias`.
4. Опишите, какие поля нужны заказчику, какие значения портал должен заполнять сам и чем нужно управлять на странице сервиса.

## Пример документа целиком

Этот пример объединяет форму одного шлюза, контакты, вкладки подключений и маршрутов, проверку имён, выбор подключения, вычисляемую колонку и действие изменения контактов.

Он рассчитан на чарт со следующими полями:

- `gateways` содержит шлюзы с полями `name` и `listeners`.
- Запись `listeners` содержит `name`, `port` и `hostname`.
- `routes` содержит записи с `name` и списком `parentRefs`.
- Запись `parentRefs` содержит `sectionName`.
- `contacts` содержит строковое поле `responsible`.
- `metadata` содержит строковые поля `creator`, `team` и `author`.
