# Панель администратора

Раздел для администраторов платформы (роль admin). Переключиться в него можно вверху бокового меню. Здесь администратор согласует публикации сервисов, управляет категориями каталога и следит за состоянием платформы.

На главной панели администратора видна сводка: сколько публикаций ждут согласования, сколько опубликовано, сколько черновиков и всего, а также очередь последних заявок и быстрые ссылки на разделы ниже.

## Согласование публикаций

Когда команда отправляет сервис на публикацию (или меняет его категорию/владельца/форму заказа), заявка попадает в очередь согласования.

В списке заявки можно отфильтровать: **Ожидают**, **Согласованные**, **Отклонённые**, **Черновики** или все сразу. Для заявки в статусе «На согласовании» доступно действие **Рассмотреть**, для остальных - **Открыть**.

На экране рассмотрения администратор видит:

- предпросмотр формы заказа и страницы сервиса в том виде, в каком их получит заказчик;
- метаданные (категория, группа-владелец) и кто отправил заявку.

Решение - **Согласовать** или **Отклонить**. При отклонении можно оставить комментарий, который увидит автор. После согласования сервис становится доступен в каталоге; об этом подробнее в разделе [Публикация сервиса](publishing).

## Категории каталога

Категории - это разделы, по которым сгруппированы сервисы в каталоге и в левом меню. Администратор управляет ими на отдельном экране:

- **Добавить категорию** - задать название, идентификатор (slug) и иконку из палитры;
- перетаскиванием изменить порядок категорий (он определяет порядок в меню);
- сменить иконку или название, удалить категорию.

> [!NOTE]
> Системную категорию «Без категории» удалить нельзя: в неё попадают автоматически найденные, ещё не разобранные сервисы.

## Стенды

Стенд - это общее для всех команд место, куда отправляются заказы сервисов, например «dev», «stage» или «prod». На отдельном экране администратор управляет стендами:

- **Добавить стенд** - указать название и кластер по умолчанию.
- Изменить название или кластер по умолчанию прямо в строке.
- Назначить другой стенд стендом по умолчанию.

> [!NOTE]
> Если вы не выберете стенд при заказе, заказ попадёт на стенд по умолчанию. При смене кластера по умолчанию уже оформленные заказы останутся в своих кластерах.

При создании стенда выберите раскладку в Git и укажите путь в GitLab. При раскладке «группа» внутри группы стенда у каждой команды своя подгруппа с репозиториями сервисов. Права в GitLab остаются разделены по командам. При раскладке «репозиторий» все заказы стенда лежат в одном репозитории в папках по команде и сервису. Выбирая эту раскладку, вы отказываетесь от разделения прав по командам в GitLab.

Укажите полный путь группы или репозитория для выбранной раскладки. Если группы или репозитория нет, портал создаст их при первом заказе. Родительская группа должна уже существовать. Стенд, созданный при обновлении портала, получил путь из прежней настройки GITLAB_GITOPS_GROUP. Раскладку и путь нельзя менять, пока на стенде есть заказы, кроме черновиков и удалённых. У стендов, созданных до появления раскладки, путь в GitLab пуст, и заказы на них не отправляются, пока путь не указан. При этом можно переименовать стенд и поменять кластер.

Поле «Режим» определяет, как стенд обрабатывает заказы. В режиме «Разворачивать» портал сохраняет файлы заказа в Git и открывает merge request. После его слияния Argo CD разворачивает сервис, а портал отслеживает статус в Argo CD. Это прежний порядок работы. В режиме «Только Git» портал создаёт те же файлы и открывает merge request. После его слияния заказ получает статус «Сохранён в Git», и обработка в портале завершается. Argo CD к стенду не подключён, файлы применяют вне портала. В режиме «Только консоль» заказ сохраняется в базе портала и сразу получает статус «Сохранён в консоли». Файлы в Git не создаются, изменения и удаление выполняются сразу, без merge request.

Режим можно изменить у стенда с заказами. Он меняется сразу, новые заказы создаются по новому режиму. Существующие заказы переводит фоновая задача по несколько заказов за проход. При переходе из режима «Только консоль» в «Только Git» или «Разворачивать» портал создаёт для каждого заказа файлы в Git и открывает запрос на слияние. После слияния заказ получает новый статус. При переходе из режима «Только Git» в «Разворачивать» заказы сразу переходят в ожидание Argo CD, без запросов на слияние. При переходе из режима «Только Git» в «Только консоль» портал открывает для каждого заказа запрос на удаление файлов из Git. После слияния заказ хранится только в консоли. Выйти из режима «Разворачивать» можно только после удаления заказов стенда. Черновики и удалённые заказы не мешают смене режима.

На странице стенда показаны статус задачи, число переведённых заказов из общего количества и список заказов, которые перевести не удалось, с причинами. Статусы задачи: «Идёт», «Завершена» и «Остановлена». Задачу можно остановить. Уже переведённые заказы останутся в новом режиме, остальные сохранят прежний режим. Пока задача идёт, менять режим, раскладку и путь стенда нельзя. Если автослияние выключено, задача ждёт ручного слияния запросов в Git.

Поле «Реестр чартов» задаёт адрес реестра, откуда Argo CD берёт чарт для заказов стенда, например `harbor.example.com` или `registry.example.com:5000`. Если поле пустое, используется реестр из глобальных настроек платформы. Каталог и проверка версий по-прежнему работают через Harbor платформы. Поэтому в другом реестре чарт должен находиться под тем же проектом, именем и версией. Команда эксплуатации настраивает доступ Argo CD к реестру. Заготовка секрета для доступа добавляется в манифесты стенда.

Перейдите из списка на страницу стенда, чтобы посмотреть его параметры, проверки и манифесты. При открытии страницы портал проверяет доступ своего токена к пути в GitLab, регистрацию кластера по умолчанию и кластеров заказов в Argo CD, а также видимость приложений по нескольким заказам. У каждой проверки есть вердикт и причина. Кнопка «Проверить снова» повторяет проверки. Для подключения Argo CD скопируйте готовые манифесты ApplicationSet или Application для раскладки «репозиторий» и секреты с токенами GitLab. Замените заглушки токенами и примените манифесты вручную один раз на стенд. Портал ничего не создаёт в Argo CD.

На странице «Стенды» нажмите «Удалить» в строке нужного стенда. Введите его имя и подтвердите удаление. Нельзя удалить последний стенд или стенд, на котором выполняется другая задача, например перевод заказов в другой режим. Чтобы удалить стенд по умолчанию, сначала назначьте другой стенд по умолчанию. Удаление выполняется в фоне и может занять время. Пока оно идёт, на стенд нельзя оформить новый заказ. Задачу можно остановить: стенд останется, но уже удалённые заказы не восстановятся. Удаление необратимо.

Портал удаляет заказы обычным путём. Черновики и заказы в режиме «Только консоль» удаляются сразу, остальные заказы удаляются через merge request на удаление файлов. Argo CD удаляет развёрнутые сервисы из кластера. После удаления всех заказов портал удаляет стенд и значения его переменных. Если группу или репозиторий стенда в GitLab создал портал, он удаляет и их. Группа, заданная в настройках платформы, и группы, созданные не порталом, сохраняются. Если часть заказов удалить не удалось, стенд остаётся. Задача показывает эти заказы и причины ошибок. Удалите их вручную и запустите удаление стенда снова. После успешного удаления стенда вручную удалите его ApplicationSet и секреты в Argo CD.

При импорте заказов из Git портал обходит путь каждого стенда. Найденные заказы он привязывает к тому стенду, по пути которого они хранятся.

Портал проверяет стенды при открытии их страниц и в фоне. Интервал фоновых проверок задаёт настройка `STAND_CHECKS_INTERVAL`, по умолчанию он составляет 5 минут. Портал проверяет доступ к пути в GitLab, кластеры и видимость приложений стенда в Argo CD и хранит последний результат. В разделе «Стенды» на странице «Состояние платформы» для каждого стенда показана карточка с худшим результатом проверок, временем последней проверки и ссылкой на страницу стенда.

Если на стенде есть заказы, но Argo CD не видит ни одного его приложения, портал показывает метку «Argo CD не подключён». После слияния запроса на изменение в Git пользователь видит в заказе заметку об ожидании подключения стенда. Администратору в заметке доступна ссылка на страницу стенда с манифестами для подключения. Проверка «Вложенные пути» предупреждает, если путь стенда в режиме «Только Git» или «Только консоль» находится внутри пути стенда в режиме «Разворачивать»: Argo CD внешнего стенда развернёт и файлы вложенного стенда. Предупреждение появляется на страницах обоих стендов.

## Переменные

Переменные - это именованные значения, на которые ссылается документ версии сервиса: домен стенда, имя дежурной команды, префикс окружения. Владелец сервиса пишет в документе ссылку `{{.Vars.ИМЯ}}`, а портал подставляет значение, когда сохраняет заказ. Так значение, общее для всех сервисов, меняется в одном месте, а не в документе каждого из них.

На странице «Переменные» добавьте переменную или удалите ненужную. Имя задаётся при создании и служит ссылкой из документа, поэтому изменить его нельзя. Используйте заглавные латинские буквы, цифры и подчёркивание. Имя должно начинаться с буквы, например `OPS_DOMAIN`. По месту можно изменить значение и описание. Описание видит владелец сервиса, когда выбирает переменную для ссылки. Укажите в нём, зачем она нужна.

У переменной может быть общее значение и своё значение для каждого стенда. Нажмите «Стенды: N из M», чтобы открыть список стендов и задать значения. Если поле для стенда пустое, портал использует общее значение. Чтобы убрать своё значение, очистите поле или нажмите крестик рядом с ним.

При сохранении заказа портал использует значение для выбранного стенда, если оно задано. Иначе портал использует общее значение. Общее значение можно оставить пустым. Если для стенда не задано своё значение, заказ с такой переменной не сохранится. Ошибка укажет имя переменной и стенд. При удалении переменной или стенда связанные значения тоже удаляются.

Новое значение попадает в новые заказы сразу после сохранения. В существующие заказы оно попадёт при следующем изменении такого заказа.

> [!NOTE]
> Это не хранилище секретов. Значение уезжает в values.yaml в Git и видно всем, у кого есть доступ к репозиторию заказов.

Переменную, на которую ссылается опубликованный документ версии, портал удалить не даст и назовёт сервисы, которые её используют: без неё их заказы перестали бы сохраняться.

## Состояние платформы

Экран показывает здоровье платформы в реальном времени (с автообновлением). Он разбит на блоки.

- **Интеграции** - внешние системы: Keycloak, Harbor, GitLab, Argo CD. Для каждой виден статус (работает или ошибка), режим и ссылка на её интерфейс.
- **Хранилища** - база данных и кэш.
- **Фоновые циклы** - внутренние процессы портала: провижининг заказов, детект дрейфа (Git), импорт из Git, автоскан каталога. Для каждого виден статус, время последнего успешного запуска и последняя ошибка, если была.

> [!TIP]
> Если заказы перестали менять статус или каталог не обновляется, начните диагностику отсюда: красный индикатор у интеграции или фонового цикла сразу укажет на причину. За детальными метриками со страницы ведёт ссылка в Grafana.
