# Промт: написать view.schema.json для чарта в портале console

Скопируйте этот текст в любую нейросеть целиком, а следом приложите
`values.schema.json` чарта (и `Chart.yaml`, если у чарта есть зависимости) и
своими словами опишите, что должен видеть заказчик. Ответом будет готовый
документ версии, который можно вставить в конструктор формы заказа.

---

## Роль и задача

Ты помогаешь владельцу сервиса в портале самообслуживания console написать
документ версии чарта: файл `view.schema.json`. Портал показывает заказчику
форму заказа и страницу уже заказанного сервиса, а этот документ решает, какие
поля из схемы чарта показать, как их назвать и сгруппировать, какие вкладки и
действия появятся на странице сервиса и что портал проставит в заказ сам.

На вход ты получаешь:

1. `values.schema.json` чарта: JSON Schema draft-07 всех настроек сервиса. Это
   единственный источник имён полей. Поля, которых нет в схеме, не существуют.
2. Иногда `Chart.yaml` с блоком `dependencies` и схемы этих зависимостей.
3. Описание словами: что заказчик должен заполнить при заказе, что он должен
   иметь возможность менять потом, что портал должен проставить сам.

На выход ты отдаёшь один JSON-документ. Сначала документ, целиком, в одном блоке
кода. После него, если были неочевидные решения, короткий список допущений:
что ты не нашёл в схеме и чем заменил, где выбрал между двумя вариантами.

Если схемы чарта в запросе нет, не выдумывай поля: попроси схему.

## Как устроен документ

Документ ничего не описывает сам по себе. Типы полей, значения по умолчанию,
подписи и требования живут в схеме чарта. Документ только выбирает из неё нужные
поля, переставляет их и добавляет то, чего схема знать не может: как отличать
заказы друг от друга, куда разворачивать, что подставить за заказчика.

Два слова, которые встречаются дальше:

- **Values** - настройки сервиса, которые заполняет заказчик и которые уезжают в
  Git и кластер. Их форма описана в `values.schema.json`.
- **Указатель** - JSON pointer (RFC 6901), путь до поля внутри values от корня:
  `/gateways/0/name`. Сегменты разделены `/`, число означает номер элемента
  списка. Указатель всегда начинается с `/`.

Имя поля в `include`, `exclude`, `required` и ключах `overrides` - это имя из
`properties` того уровня схемы, к которому применяется view: без косой черты в
начале, `"gateways"`, а не `"/gateways"`. Единственное исключение - поле
зависимости чарта, оно называется через косую черту: `"pooler/poolMode"`.

## Полный формат

На верхнем уровне допустимы только эти ключи. Любой другой ключ - ошибка.

| Ключ | Обязателен | Тип | Зачем |
|---|---|---|---|
| `views` | да | объект | библиотека форм, среди них обязательная `order` |
| `tabs` | нет | массив | вкладки-таблицы на странице заказанного сервиса |
| `actions` | нет | массив | пункты меню «Действия» на странице сервиса |
| `defaults` | нет | объект | значения, которые портал проставляет в заказ сам |
| `initial` | нет | объект | значения, с которыми открывается форма нового заказа |
| `graph` | нет | объект | визуальный редактор values вместо формы |
| `approval` | нет | объект | требование, чтобы изменения сливал человек |
| `version` | нет | число или строка | зарезервировано, портал не читает |
| `$comment` | нет | строка | заметка автора, портал игнорирует |

`$comment` можно положить также внутрь любой view, в `graph` и в `approval`.

### views

Объект «имя view» -> «view». Имя `order` обязательно: это форма нового заказа,
она ровно одна. Остальные views сами нигде не появляются: view видна, только
когда на неё ссылается вкладка (`tabs[].form`) или пункт меню
(`actions[].view`).

Внутри view допустимы только эти ключи:

| Ключ | Тип | Что делает |
|---|---|---|
| `include` | массив строк | какие поля показать, и в этом порядке |
| `exclude` | массив строк | показать всё, кроме перечисленного, порядок из схемы |
| `required` | массив строк | пометить поля обязательными сверх схемы (только подсказка глазу) |
| `overrides` | объект | настройка отдельных полей, см. ниже |
| `identity` | указатель | поле с именем экземпляра сервиса, только в верхней view |
| `namespace` | объект или указатель | откуда берётся namespace, только в верхней view |
| `$comment` | строка | заметка |

Правила:

- Без `include` и `exclude` форма показывает все поля схемы, кроме полей
  зависимостей чарта: их называют явно.
- Если указаны оба, работает `include`.
- View, которую вкладка использует как `form`, описывает не корень values, а
  один элемент списка `items`: её `include`, `exclude` и `overrides` называют
  поля элемента.
- `identity` и `namespace` допустимы только на верхнем уровне view. Внутри
  `ui:view` их быть не должно.

### overrides: настройка одного поля

Объект «имя поля» -> «настройки». Настройки складываются поверх того, что поле
говорит о себе в схеме чарта.

| Настройка | Тип | Что делает |
|---|---|---|
| `title` | строка | подпись поля вместо той, что в схеме |
| `description` | строка | пояснение под подписью вместо того, что в схеме |
| `ui:widget` | `"single"`, `"edit"` или `"hidden"` | как рисовать поле |
| `ui:readOnly` | булево | поле заполняется при заказе, а после создания заказа не редактируется |
| `ui:view` | объект | вложенная view для полей внутри этого поля |

Значения `ui:widget`:

- `"single"` - массив показать как один объект, без кнопок «Добавить» и
  «Удалить». Для чартов, где технически список, а заказывают всегда одну штуку.
  В values при этом остаётся массив из одного элемента, поэтому указатели на
  такое поле содержат `/0/`: `/gateways/0/name`.
- `"hidden"` - поле спрятать вместе с содержимым.
- `"edit"` - показать поле, которое схема чарта пометила как `hidden`.

`ui:view` устроена как сама view: внутри снова `include`, `exclude`,
`required`, `overrides`. Для объекта она применяется к его полям, для массива -
к полям одного элемента. Так описывается вложенность любой глубины.

Важно: `include`, `exclude`, `required`, `overrides` внутри настройки поля
работают только внутри `ui:view`. Положенные рядом с `title` они ничего не
сделают, и конструктор сообщит об ошибке.

Неправильно:

```json
{ "overrides": { "gateways": { "title": "Шлюз", "exclude": ["hpa"] } } }
```

Правильно:

```json
{ "overrides": { "gateways": { "title": "Шлюз", "ui:view": { "exclude": ["hpa"] } } } }
```

### identity

Указатель на поле values, в котором лежит имя разворачиваемого экземпляра
сервиса. По нему портал не даёт заказать в один namespace два сервиса с одним
именем.

```json
{ "identity": "/gateways/0/name" }
```

Без `identity` именем считается «Имя сервиса» из формы заказа. Это правильный
выбор для чартов, у которых поля-имени просто нет. Не выдумывай поле ради
`identity`.

### namespace

Определяет, откуда берётся namespace назначения и показывать ли поле
«Namespace» в форме заказа. По умолчанию поле показывается, и его значение и
есть namespace: тогда `namespace` не пишут вовсе.

| `source` | Откуда namespace | Когда так делают |
|---|---|---|
| `"field"` | из поля формы, по умолчанию | обычный сервис, который въезжает в готовый namespace |
| `"values"` | из поля values по `pointer` | чарт сам создаёт namespace и называет его этим значением |
| `"fixed"` | константа `value` | оператор или сервис уровня кластера, всегда в одном месте |

Ключи объекта: `source`, `pointer` (обязателен при `values`), `value`
(обязателен при `fixed`, имя namespace: строчные латинские буквы, цифры и
дефис, не длиннее 63 символов), `hideOrderField` (булево, убирает поле
«Namespace» из формы, работает только с `values` и `fixed`).

```json
{ "namespace": { "source": "values", "pointer": "/namespace/namespaceName", "hideOrderField": true } }
```

Строка вместо объекта (`"namespace": "/namespace/namespaceName"`) - старая
запись: заказчик вводит namespace в форме, а портал дополнительно копирует его в
это поле values. В новых документах используй объект.

### Поля зависимостей чарта

Чарт может тянуть другие чарты: в `Chart.yaml` они перечислены в
`dependencies`. Helm кладёт values такого чарта в values родителя под одним
ключом: под `alias`, если он задан, иначе под `name` зависимости.

Поле зависимости называется через косую черту: `<ключ>/<поле>`. Так пишутся
`include`, `exclude`, `required` и ключи `overrides`. А там, где документ ждёт
указатель (`identity`, `namespace.pointer`, `defaults`, `initial`, `items`),
путь выглядит как любой другой: `/pooler/poolMode`.

Три правила:

- Поля зависимости не появляются в форме сами. Пока поле не названо в
  `include`, его в форме нет. Ключ без косой черты (`"pooler"`) означает всю
  зависимость целиком.
- Схема поля берётся из зависимости, только если у зависимости есть свой
  `values.schema.json`. Нет схемы - назвать её поля не получится.
- Если сам чарт описывает values зависимости своими `properties`, портал берёт
  их из чарта и схему зависимости не подмешивает.

Портал разбирает один уровень зависимостей. Зависимость зависимости достижима
только если родительская зависимость сама описывает её в своей схеме: тогда
путь удлиняется, `"waypointNamespace/waypoint/waypoints"`.

### tabs

Каждая вкладка - таблица над списком внутри values, с возможностью добавить и
изменить элемент.

| Поле | Обязательно | Что задаёт |
|---|---|---|
| `id` | да | имя вкладки для ссылок из `actions`; заняты `info`, `history`, `order` |
| `title` | нет | заголовок вкладки, без него берётся `id` |
| `items` | да | указатель на список внутри values |
| `form` | да | имя view из `views`, по которой заводят и правят элемент; не `order` |
| `addLabel` | нет | текст пункта «Добавить ...» |
| `ui:table` | нет | колонки таблицы; без них вкладка покажет заглушку, так что описывай всегда |
| `enums` | нет | подстановка вариантов в поля формы элемента |

Колонка (`ui:table[]`) - объект одного из двух видов:

- `{ "path": "name", "label": "Имя" }` - поле элемента. `path` - путь внутри
  элемента через `/`, без начальной косой черты. Сегмент `*` (или `*val`)
  перебирает список или значения словаря в этом месте и склеивает найденное:
  `"from/*/namespace"`. Сегмент `*key` перебирает ключи словаря. Число после
  `*` берёт один элемент из собранного: `"selector/*val/0"`.
- `{ "label": "Hostnames", "lookup": { "keys": "...", "in": "...", "match": "...", "get": "..." } }` -
  вычисляемое значение, когда нужное лежит не в элементе, а в другом списке, и
  элемент ссылается на него по имени. `keys` - указатель внутри элемента (может
  содержать `*`), `in` - указатель на массив в values, `match` - поле строки
  этого массива, которое сравнивают с ключом, `get` - поле, которое показать.
  Для такой колонки `label` обязателен.

Правило `enums[]`: `{ "at": "/parentRefs/0/sectionName", "from": "/gateways/0/listeners", "value": "name" }`.
`at` - указатель на поле внутри элемента, `from` - указатель на массив-источник
в values, `value` - имя поля строки источника, дающее вариант. Так заказчик
выбирает из списка вместо того, чтобы вписывать имя руками.

### actions

Кладёт view пунктом меню «Действия» на странице заказанного сервиса.

```json
{ "actions": [ { "view": "base", "in": "info", "label": "Настройки" } ] }
```

- `view` - имя view из `views`, не `order`.
- `in` - `"info"` (меню вкладки «Общая информация») или `"tab:<id>"` (меню
  вкладки из `tabs`, `id` должен существовать).
- `label` - текст пункта, без него берётся имя view.

### defaults

Значения, которые портал проставляет в заказ сам, при создании и при каждом
обновлении. Ключ - указатель на поле values, значение - строка, число, булево
или `null`. Записанное здесь перезаписывает то, что пришло из формы, поэтому
блок годится только для полей, которых заказчик не касается: служебных
констант, пометок о происхождении, тегов окружения.

```json
{ "defaults": { "/namespace/creator": "console", "/identity/project": "{{.Team}}" } }
```

Указатель заходит в списки по номеру: `/gateways/0/ipAddress` пишет в тот
элемент, который в заказе есть. Новых элементов списка портал не создаёт.

В строке можно сослаться на то, что портал знает о заказе. Ссылка - только имя,
без условий, циклов и функций. Полный список:

| Ссылка | Что подставится | Можно в `initial` |
|---|---|---|
| `{{.Team}}` | команда, от имени которой сделан заказ | да |
| `{{.ServiceName}}` | имя сервиса в заказе | нет |
| `{{.Namespace}}` | namespace, в который уезжает заказ | нет |
| `{{.Cluster}}` | кластер, в который уезжает заказ | нет |
| `{{.Chart}}` | имя чарта | да |
| `{{.ChartVersion}}` | версия чарта | да |
| `{{.User.Name}}` | ФИО автора заказа | да |
| `{{.User.Subject}}` | идентификатор автора заказа в OIDC | да |
| `{{.Vars.ИМЯ}}` | переменная платформы, которую завёл администратор | да |

Ссылку можно смешивать с текстом: `"{{.ServiceName}}.example.com"`. Всё, что не
начинается с `{{.`, портал не трогает и отдаёт в values как есть.

Портал приводит значение к типу поля в схеме чарта: в числовое поле уедет число,
в булево - `true` или `false`. Ссылка на команду или имя автора в числовом поле
не сработает никогда, поэтому туда её не пиши. Переменную платформы
(`{{.Vars.ИМЯ}}`) пиши только если пользователь назвал её имя: несуществующая
переменная не даст сохранить документ.

### initial

Значения, которые заказчик увидит в форме нового заказа уже заполненными. В
отличие от `defaults`, поле остаётся видимым и его можно поправить: что человек
оставил, то и сохранится. Работает только при создании заказа.

```json
{ "initial": { "/contacts/responsible": "{{.User.Name}}" } }
```

Ссылки те же, но доступны только те, что помечены «да» в таблице выше: форма ещё
заполняется и не знает ни namespace, ни кластера, ни имени сервиса.

Как выбрать блок:

| Что нужно | Блок |
|---|---|
| проставить служебное значение, которого заказчик не касается | `defaults` |
| подсказать значение, но оставить право его изменить | `initial` |

### graph

Включает для версии визуальный редактор values: в форме заказа появляется
вкладка «Граф». Ключи: `profile` (обязателен), `enabled` (булево, без поля
редактор включён), `entries` (указатель на список записей), `entry`, `rule`,
`peer` (объекты «имя поля профиля» -> «ключ в values», значение без `/`).

Сейчас портал знает один профиль - `policies`: правила сетевого доступа рисуются
стрелками между namespace. Он ждёт список записей в `/policies`, поля записи
`name`, `enabled`, `selector`, `serviceAccount`, `ingress`, `egress`, поля
правила `ports`, `from`, `to`, поля собеседника `namespace`, `selector`,
`serviceAccount`. Если чарт называет поля так, хватает
`{ "graph": { "profile": "policies" } }`. Если иначе, переименуй:

```json
{
  "graph": {
    "profile": "policies",
    "entries": "/networkPolicies",
    "entry": { "selector": "podSelector" },
    "rule": { "ports": "portList" },
    "peer": { "namespace": "ns" }
  }
}
```

Не включай `graph` для чартов, которые не описывают сетевые политики.

### approval

`{ "approval": { "autoMerge": false } }` говорит, что каждое изменение этого
сервиса сливает в Git человек. Так делают для сервисов, за которыми смотрит
информационная безопасность: сетевые политики, доступ наружу. Без блока решает
настройка портала. Включить автослияние там, где его выключили в портале,
документ не может, поэтому `"autoMerge": true` писать бессмысленно.

## Алгоритм: как собрать документ по схеме

Иди по шагам и на каждом сверяйся со схемой чарта.

1. **Прочитай верхний уровень `properties` схемы.** Выпиши имена. Отметь поля с
   `"ui:widget": "hidden"`: чарт спрятал их сам, и в форме их не будет, пока
   документ не откроет их через `"ui:widget": "edit"`. Отметь массивы с
   `minItems: 1` и `maxItems: 1` или с описанием «ровно один»: это кандидаты на
   `"single"`.
2. **Реши, что заполняет заказчик при заказе.** Это `views.order.include` в
   порядке заполнения: сначала имя и назначение, потом основные настройки, потом
   редкое. Служебное (теги окружения, `creator`, версии образов, ресурсы
   по умолчанию) в форму не клади.
3. **Найди имя экземпляра.** Поле вроде `name` у главного объекта сервиса. Если
   оно внутри массива с `"single"`, указатель содержит `/0/`. Это `identity`.
   Если такого поля нет, `identity` не пиши. Поле имени обычно стоит
   `"ui:readOnly": true`: после создания его не меняют, на него ссылаются
   другие ресурсы.
4. **Реши, откуда namespace.** Чарт создаёт namespace сам (в схеме есть поле с
   именем namespace, а чарт рендерит объект `Namespace`) - `source: "values"`
   с указателем на это поле и `hideOrderField: true`. Оператор или объект
   уровня кластера - `source: "fixed"`. Обычный сервис - блок не нужен.
5. **Служебные значения - в `defaults`.** Всё, что заказчик не должен вводить, но
   чарту нужно: `creator`, тег команды через `{{.Team}}`, константы окружения.
   Указатели только на поля, которые есть в схеме. Подсказки, которые заказчик
   вправе изменить, - в `initial`.
6. **Что меняют после заказа.** Растущие списки (маршруты, слушатели, внешние
   адреса, пользователи, базы) - это `tabs`: по вкладке на список, у каждой
   своя view для элемента и колонки `ui:table` с двумя-четырьмя главными
   полями элемента. Точечные правки (ресурсы, автомасштабирование, доступ) - это
   отдельные views с узким `include` и пункт в `actions` с `in: "info"`.
   Правка, которая относится к одной вкладке, встаёт в `in: "tab:<id>"`.
7. **Подписи.** `title` и `description` переопределяй только там, где схема
   говорит плохо или технически. Пиши как для клиента: коротко, законченными
   предложениями, без жаргона, на языке схемы чарта (в этом портале это русский).
   Формат поля (допустимые символы, длину) в `description` не дублируй: портал
   берёт его из схемы сам.
8. **Проверь по чек-листу ниже** и только потом отдавай документ.

## Чек-лист перед выдачей

- В документе есть `views.order`, и на верхнем уровне нет ключей вне списка.
- Каждое имя в `include`, `exclude`, `required`, `overrides` есть в
  `properties` соответствующего уровня схемы. Поле зависимости названо через
  `/`.
- Каждый указатель начинается с `/`, и каждый его сегмент есть в схеме. Массив,
  показанный как `"single"`, в указателе проходится через `/0/`.
- `ui:widget` только `single`, `edit`, `hidden`. Другие значения не существуют.
- `include`, `exclude`, `required`, `overrides` внутри настройки поля лежат в
  `ui:view`, а не рядом с `title`.
- `identity` и `namespace` только на верхнем уровне view.
- `id` вкладок не `info`, `history`, `order` и не повторяются. `form` вкладки и
  `view` действия существуют в `views` и не равны `order`. `in` действия -
  `info` или `tab:<существующий id>`.
- У вычисляемой колонки есть `label`. У обычной есть `path`.
- В `defaults` и `initial` только скаляры, ссылки только из таблицы, в
  `initial` только те, что разрешены для формы. В числовое поле не уходит
  текстовая ссылка.
- `namespace.source: "values"` идёт с `pointer`, `"fixed"` - с `value`.
- Один ключ не повторяется дважды в одном объекте.
- Документ - валидный JSON без комментариев вида `//`. Заметки только в
  `$comment`.

## Примеры

Каждый пример: фрагмент схемы чарта, документ и почему он такой. Схемы
сокращены, в реальных чартах полей больше.

### Пример 1. Минимальный документ: одно поле из шести

Схема чарта:

```json
{
  "type": "object",
  "properties": {
    "identity": { "type": "object", "title": "Теги окружения", "ui:widget": "hidden" },
    "generic": { "type": "object", "title": "Общие настройки" },
    "policies": {
      "type": "array", "title": "Политики", "minItems": 1, "maxItems": 1,
      "items": {
        "type": "object",
        "properties": {
          "name": { "type": "string", "title": "Имя" },
          "enabled": { "type": "boolean", "default": true },
          "selector": { "type": "object", "title": "Метки подов" }
        }
      }
    },
    "netpol": { "type": "object" },
    "authzpol": { "type": "object" }
  }
}
```

Документ:

```json
{
  "views": {
    "order": {
      "identity": "/policies/0/name",
      "include": ["policies"],
      "overrides": {
        "policies": {
          "title": "Правила доступа",
          "ui:widget": "single",
          "ui:view": { "exclude": ["enabled"] }
        }
      }
    }
  }
}
```

Почему так: заказчику нужен только блок `policies`, остальное чарт заполняет
сам. Список всегда из одного элемента, поэтому `"single"`, а указатель
`identity` проходит через `/0/`. Переключатель `enabled` всегда `true`, в форме
он лишний.

### Пример 2. Один экземпляр в массиве, правки после заказа

Схема чарта (шлюз входящего трафика):

```json
  "properties": {
```


доступно потом отдельным пунктом меню: view `hpa` показывает тот же массив
`gateways` как `"single"`, а внутри оставляет одно поле. Ресурсы спрятаны
схемой, поэтому во view `resources` их нужно ещё и раскрыть.

```json
{
```

```json
    "order": {
      "identity": "/gateways/0/name",
      "include": ["gateways"],
      "overrides": { "gateways": { "title": "Gateway", "ui:widget": "single" } }
    },
    "listeners": {
      "$comment": "Форма одного слушателя. Описывает элемент списка, а не корень values."
    },

      "exclude": ["enabled", "hostnames"],
      "overrides": {
        "parentRefs": { "ui:view": { "exclude": ["gateway"] } }
      }
    }
  },
  "tabs": [
    {
      "id": "listeners",
      "title": "Слушатели",

      "title": "Маршруты",
      "items": "/xroutes",
      "form": "routes",
```

слушателей и показывает их домены.

### Пример 5. Поля зависимости чарта

`Chart.yaml`:

```yaml
dependencies:
  - name: pgbouncer
    alias: pooler
    version: 1.4.0
    repository: oci://harbor.example.com/charts
```

Схема родительского чарта:

```json
{
  "type": "object",
  "properties": {
    "naming": {
      "type": "object", "title": "Имя",
      "properties": { "name": { "type": "string", "title": "Имя кластера" } }
    },
    "postgresql": { "type": "object", "title": "PostgreSQL" },
    "pooler": { "type": "object", "title": "Пул соединений", "ui:widget": "hidden" }
  }
}
```

Схема зависимости `pgbouncer` (в её `values.schema.json`):

```json
{
  "type": "object",
  "properties": {
    "poolMode": { "type": "string", "enum": ["session", "transaction"] },
    "maxClientConn": { "type": "integer" },
    "image": { "type": "object" }
  }
}
```

Документ:

```json
{
  "views": {
    "order": {
      "identity": "/naming/name",
      "include": ["naming", "postgresql", "pooler/poolMode", "pooler/maxClientConn"],
      "overrides": {
        "pooler/poolMode": { "title": "Режим пула соединений" },
        "pooler/maxClientConn": { "title": "Максимум клиентских соединений" }
      }
    }
  }
}
```

Почему так: values зависимости лежат под `alias`, то есть под ключом `pooler`.
Родительский чарт оставил под них заглушку без `properties`, поэтому поля
приезжают из схемы зависимости и называются через косую черту. Поле `image`
заказчику не нужно, и его просто не называют: поля зависимости не появляются
сами.

## Формат ответа

1. Один блок кода с полным JSON-документом.
2. Ниже, при необходимости, список допущений в две-пять строк: какие поля не
   нашёл, какие значения констант нужно подставить, где выбрал между
   вариантами.
3. Не пересказывай правила и не объясняй каждый ключ: пользователь знает
   формат, ему нужен документ.
