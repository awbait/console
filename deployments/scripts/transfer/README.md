# Перенос релиза в контур

Три скрипта переносят то, что публикуется на GitHub, в стенд: образы консоли в
Harbor, Helm-чарты в GitLab (а оттуда пайплайном в Harbor) и сами исходники на
машину, с которой всё это запускается.

| Скрипт | Что переносит | Откуда | Куда |
|---|---|---|---|
| `update-repos.ps1` | исходники `console` и `console-charts` | ветка `main` обоих репозиториев | папка, из которой запущен |
| `sync-images.ps1` | образы `portal` и `collector` | GitHub Release репозитория `awbait/console` | `harbor.example.test/core/console/*` |
| `sync-charts.ps1` | Helm-чарты | ветка `main` репозитория `awbait/console-charts` | проекты чартов в GitLab, дальше Harbor |

Все три идемпотентны и убирают за собой: скачанные архивы, временные клоны и
локальные образы удаляются в конце. Оставить их можно флагом `-Keep`.

Git на этих машинах нет, ssh-доступа к GitHub тоже, поэтому исходники везде
приезжают zip-архивом по https, а не клоном.

## 0. Исходники на машине переноса

Машина переноса держит оба репозитория рядом, и остальные два скрипта запускаются
из этой копии:

```
<рабочая папка>\
  charts-map.json     <- ваша карта чартов, её никто не трогает
  console\
  console-charts\
```

Всё, что принадлежит установке, лежит рядом с репозиториями, а не внутри
них: `update-repos.ps1` заменяет папку репозитория целиком, и положенное
внутрь пропадает при первом же обновлении.

`update-repos.ps1` обновляет обе копии. Запускать из этой самой папки:

```powershell
# обновить оба репозитория
powershell -File console\deployments\scripts\transfer\update-repos.ps1

# только чарты
powershell -File console\deployments\scripts\transfer\update-repos.ps1 -Repos console-charts

# конкретная версия консоли, старую копию оставить рядом
powershell -File console\deployments\scripts\transfer\update-repos.ps1 -Ref v0.12.0 -Repos console -Keep
```

Что происходит по шагам:

1. Определяется коммит, на который смотрит ветка или тег (`gh`, при его
   отсутствии - публичный GitHub API).
2. Каждая копия носит файл `.transfer-source.json` с именем репозитория, ref и
   коммитом. Если ref всё ещё смотрит туда же, копия не трогается. Скачать
   заново: `-Force`.
3. Архив распаковывается рядом, и только целиком распакованное дерево встаёт на
   место. Старая копия перед этим отъезжает в `<repo>.previous` и удаляется
   после успеха, а с `-Keep` остаётся: неудачный перенос откатывается
   переименованием.
4. Копия, оказавшаяся рабочей копией git (есть `.git`), не трогается: замена
   выбросила бы историю и незакоммиченное. Обновляй её через git или передай
   `-Force`.

Скрипт лежит внутри `console` и обновляет в том числе `console`. Windows это
позволяет: `.ps1` читается целиком до запуска, и файл не остаётся открытым.
Чего Windows не позволяет - переименовать папку, внутри которой кто-то стоит,
поэтому `console` обновляется последним, а сам скрипт работает из родительской
папки. Открытая внутри консоль, редактор или проводник остановят замену, и
скрипт скажет, какая это была папка.

Путь длиннее 260 символов Windows PowerShell не запишет. Имя папки, из которой
запускаешь, лучше держать коротким: к нему добавляются 48 символов имени папки
внутри архива и до 70 - самого глубокого файла в репозитории.

## 1. Образы

```powershell
# последний релиз, оба образа
powershell -File deployments\scripts\transfer\sync-images.ps1

# конкретная версия, только портал
powershell -File deployments\scripts\transfer\sync-images.ps1 -Version v0.8.1 -Components portal
```

Что происходит по шагам:

1. Проверяется docker. Если демон не отвечает, скрипт сам запускает Docker
   Desktop и ждёт до 5 минут; если Docker не установлен, говорит об этом прямо.
2. Версия берётся из последнего релиза (`gh`, при его отсутствии - публичный
   GitHub API) или из `-Version`.
3. `docker login` в Harbor. Логин идёт первым: без него проверка «образ уже
   есть?» на приватном проекте отвечала бы «нет».
4. Для каждого образа проверяется `harbor.example.test/core/console/<имя>:<версия>`.
   Всё, что уже там, пропускается. Если пропускать нечего, скрипт завершается,
   ничего не скачав. Перезалить принудительно: `-Force`.
5. Скачивается `console-<имя>-<версия>-linux-amd64.tar.gz` и сверяется с
   `SHA256SUMS.txt` из релиза.
6. `docker load`, перетегирование, `docker push`, проверка, что тег читается из
   реестра.
7. Уборка: архивы и локальные образы удаляются.

Ссылка на образ внутри архива не захардкожена: скрипт берёт её из вывода
`docker load`, так что переезд публикации с ghcr.io ничего не сломает.

Учётные данные Harbor: параметры `-HarborUser` / `-HarborPassword`, иначе
`$env:HARBOR_USER` / `$env:HARBOR_PASSWORD`, иначе стендовые `admin` /
`Harbor12345`. Пароль передаётся через `--password-stdin`, а не `--password`:
второй вариант светит его в списке процессов и в истории оболочки.

Учётной записи нужно право push в проект, куда кладутся образы (`core` в примере
выше): в Harbor это роль Developer и выше, либо робот с `push` и `pull` на этом
проекте. Логин идёт первым шагом ещё и поэтому: без него проверка «образ уже
есть?» на приватном проекте ответила бы «нет» и скрипт залил бы всё заново.

Если в релизе нет архива для какого-то компонента (старые релизы), скрипт
скажет об этом и продолжит с остальными - это не ошибка.

## 2. Чарты

У `console-charts` нет ни релизов, ни тегов: чарты живут на ветке, а версия у
каждого своя, в его `Chart.yaml`. Поэтому единица переноса тут - чарт, а не
релиз, и «уже перенесено» означает «копия в GitLab совпадает с гитхабовской» с
точностью до двух правок: сохранённых файлов из `keep` и зависимостей,
перецепленных на Harbor.

```powershell
# посмотреть план, ничего не меняя
powershell -File deployments\scripts\transfer\sync-charts.ps1 -DryRun

# перенести всё: ветка + MR в каждом проекте чарта
powershell -File deployments\scripts\transfer\sync-charts.ps1

# один чарт, и сразу в Harbor, минуя пайплайн
powershell -File deployments\scripts\transfer\sync-charts.ps1 -Charts ingress-gateway -PushToHarbor

# не ждать человека: GitLab сольёт MR сам, когда пайплайн станет зелёным
powershell -File deployments\scripts\transfer\sync-charts.ps1 -AutoMerge
```

### Карта чартов

Скрипт ничего не угадывает: куда какой чарт класть, написано в
`charts-map.json`. Чарт с пустым `project` - это ошибка конфигурации, и скрипт
назовёт такие чарты и остановится, не тронув GitLab.

**Заполненную карту держите рядом с папкой `console`, а не внутри неё.**
`update-repos.ps1` заменяет репозиторий целиком, и карта, заполненная внутри,
пропадёт вместе со всем остальным. Скрипт ищет её в таком порядке:

1. `-ConfigPath <путь>`;
2. `$env:CHARTS_MAP`;
3. `charts-map.json` рядом с папкой `console` - на это и рассчитано, флаг не
   нужен;
4. шаблон, лежащий в самом репозитории, рядом со скриптами.

Какую карту прочитал, скрипт печатает первой строкой. Если он дошёл до шаблона
из репозитория и там пустые `project`, то так и скажет: скопируйте файл на
уровень выше и заполните там.

Адреса `gitlabUrl` и `harborHost` шаблон тоже не несёт: они принадлежат
установке, а не продукту, и подставленный по умолчанию чужой адрес означал бы
чарты, уехавшие не туда. Пустые - скрипт назовёт их и остановится.

```json
{
  "gitlabUrl": "https://gitlab.example.test",
  "targetBranch": "main",
  "harborHost": "harbor.example.test",
  "harborProject": "platform",
  "keep": ["values.yaml"],
  "charts": {
    "ingress-gateway": { "project": "platform/charts/ingress-gateway" },
    "waypoint":        { "project": "team-net/helm/waypoint" },
    "console":         { "project": "platform/charts/console", "harborProject": "core" }
  }
}
```

| Поле | Что задаёт |
|---|---|
| `gitlabUrl` | адрес GitLab; полный путь проекта берётся из `charts.<имя>.project` |
| `targetBranch` | ветка, от которой берётся копия и в которую нацелен MR |
| `keep` | файлы, которые остаются гитлабовскими; переопределяется на уровне чарта |
| `harborProject` | проект Harbor по умолчанию (`oci://<host>/<project>/<chart>`) |
| `charts.<имя>.project` | путь проекта чарта в GitLab, обязателен |
| `charts.<имя>.keep` | свой список сохраняемых файлов вместо общего; пустой (`[]`) - перетереть всё, включая values.yaml |
| `charts.<имя>.harborProject` | свой проект Harbor вместо общего; сюда же перецепляются зависимости на этот чарт |

Формат JSON, а не YAML, намеренно: `ConvertFrom-Json` встроен в PowerShell, и
скрипту не нужен ни `yq`, ни сторонний модуль.

### Что делает перенос

Источник скрипт скачивает zip-архивом по https (`github.com/<repo>/archive/<sha>.zip`),
а не клонирует: машинам стенда git-доступ к GitHub не нужен, читаемого дерева
достаточно. Архив качается по SHA коммита, в который резолвится `ref`, так что в
GitLab уезжает ровно тот коммит, который назван в MR. Git нужен только для
GitLab-стороны.

Дальше для каждого чарта из карты:

1. Клонируется проект чарта из GitLab (ветка `targetBranch`). Проект должен
   существовать: скрипт его не создаёт, а говорит, что клон не удался, и идёт
   дальше.
2. Файлы из `keep` откладываются в сторону. Всё остальное содержимое проекта
   удаляется и заменяется версией из `console-charts`. Отложенные файлы
   возвращаются последними, поэтому гитлабовский `values.yaml` перекрывает
   гитхабовский. Файл из `keep`, которого в GitLab не было, приезжает из GitHub.
3. Зависимости в `Chart.yaml` перецепляются на Harbor (см. ниже).
4. Если после этого ничего не изменилось, MR не создаётся. С `-PushToHarbor`
   прогон всё равно идёт дальше, в Harbor: это отдельный вопрос, и ответ на
   него бывает другим.
5. Иначе создаётся ветка `chore/sync-<чарт>-<версия>`, коммит по Conventional
   Commits (в теле - откуда взято и что сохранено), и `git push` с push-опциями
   GitLab, который сразу открывает MR в `targetBranch`. Ссылку на MR печатает
   сам GitLab в выводе push.
6. Если ветка на удалённой стороне уже есть, она осталась от прошлого прогона:
   имя ветки выдаёт только этот скрипт. Скрипт скажет об этом и заменит её.
   Открытый на ней MR получит новый коммит, второй MR GitLab не откроет.

Дальше чарт попадает в Harbor пайплайном самого проекта чарта, по слитому MR.
Слить MR по умолчанию должен человек: это точка, где видно, что именно уезжает в
контур.

С флагом `-AutoMerge` кнопку нажимать не нужно: MR всё так же создаётся и
показывает содержимое переноса, а сливает его сам скрипт, как только пайплайн
проекта становится зелёным. Прогон при этом не завершается после push, а
остаётся ждать пайплайны: сначала зависимостей, потом всех остальных MR разом.
Сколько ждать, задаёт `-AutoMergeTimeout` в минутах (по умолчанию 30). MR,
который за это время не слился, остаётся открытым и попадает в отчёт с
последним увиденным состоянием и ссылкой; повторный прогон подхватит его.

Почему сливает скрипт, а не GitLab. К push добавляется и родная опция
`merge_request.merge_when_pipeline_succeeds`, но до GitLab 18.8 она в
большинстве случаев не срабатывает: воркер автомержа, проснувшись на зелёном
пайплайне, читает статус слияния в этот же момент, и если статус переходный
(`checking`, `approvals_syncing`), молча выходит и больше не пробует. Заново
проверку запускает только открытие страницы MR, поэтому такой MR сливается в
ту секунду, когда его открывают в браузере, и никогда раньше. Это баг GitLab
[#592733](https://gitlab.com/gitlab-org/gitlab/-/issues/592733), исправлен в
18.8 за фича-флагом `auto_merge_on_merge_status_change`. Скрипт делает то,
что сделал бы человек: следит за пайплайном и сливает MR через API. Родная
опция остаётся на случай, если GitLab уже исправлен или прогон оборвался: там,
где она работает, MR сольётся и без скрипта, а слитый MR слитым и останется.

Что видно в выводе: строка на каждое изменение состояния MR (пайплайн, статус
слияния), отказ GitLab слить с его причиной и итоговое `merged`. Отказ с
переходным статусом повторяется на следующем круге, с окончательным
(конфликт, draft, запрошены правки) ожидание этого MR заканчивается сразу.

Проект без пайплайна ждать нечего: если через три минуты пайплайна так и нет,
а GitLab считает MR пригодным к слиянию, скрипт его сливает. Так живут вместе
`-AutoMerge` и `-PushToHarbor`, скрипт об этом только предупреждает.

MR ищется по ветке, а не по заголовку. Если с прошлого прогона в проекте уже
висит открытый MR для этой ветки, повторный прогон кладёт новый коммит в него:
GitLab второй MR на ту же ветку не открывает. Скрипт находит этот же MR и
дальше ведёт его как свой.

### Зависимости

На GitHub чарты лежат в одном репозитории рядом друг с другом, поэтому
зависимость там записана как `file://../<чарт>`: так `console` тянет
`ingress-gateway`, а `namespace` - `waypoint`. В GitLab у каждого чарта свой
проект, соседнего каталога рядом нет, и такая ссылка не резолвится ни при
`helm package`, ни в пайплайне.

Поэтому при переносе каждая такая ссылка заменяется на проект зависимости в
Harbor:

```yaml
# на GitHub
repository: "file://../ingress-gateway"
# в GitLab
repository: "oci://harbor.example.test/platform"
```

Имя чарта остаётся в `name:`, поэтому в `repository` идёт только проект.
Проект берётся из карты: `harborProject` самой зависимости, иначе общий. Правка
детерминированная, так что на следующем прогоне копия в GitLab совпадёт и чарт
будет пропущен.

Зависимость должна попасть в Harbor раньше чарта, который её требует: и
пайплайн проекта, и `-PushToHarbor` пакуют чарт, скачивая зависимости из Harbor.
Порядок скрипт не берёт из карты, а читает из самих `Chart.yaml`: зависимость
идёт первой, в остальном порядок карты сохраняется. Если он отличается от
карты, скрипт печатает, в каком порядке пойдёт.

Порядка мало: MR зависимости должен слиться, а её пайплайн опубликовать чарт, и
только потом пайплайн зависимого чарта сможет собраться. Поэтому перед тем как
открыть MR, скрипт спрашивает Harbor про каждую зависимость в нужной версии:

- есть - MR открывается;
- нет, а MR зависимости открыт в этом же прогоне с `-AutoMerge` - скрипт
  сначала сливает этот MR (дождавшись его пайплайна), потом ждёт, пока
  пайплайн целевой ветки положит зависимость в Harbor, и только тогда идёт
  дальше. На каждое ожидание отводится `-AutoMergeTimeout` минут (по умолчанию
  30). Не дождался - чарт попадает в отчёт как несделанный, MR не открывается:
  с красным пайплайном MR всё равно не слился бы;
- нет, и ждать нечего (без `-AutoMerge` MR сливает человек, либо зависимость
  вообще не трогалась в этом прогоне) - чарт пропускается, скрипт говорит, что
  сделать: слить MR зависимости и дождаться её пайплайна, либо проверить,
  почему пайплайн зависимости не опубликовал её, и перезапустить с
  `-Charts <чарт>`.

Так же ведёт себя прогон по одному чарту (`-Charts console`): скрипт скажет,
чего именно не хватает в Harbor.

Про Harbor спрашивается через его REST API, helm для этого не нужен. Учётная
запись та же, что у `-PushToHarbor` (см. «Доступы»); публичный проект отвечает
и без неё.

### `-PushToHarbor`

Для репозиториев, где пайплайна ещё нет. Скрипт делает `helm package` и
`helm push` сам, причём пакует из клона уже после подмены файлов, так что в
Harbor уезжает ровно то, что будет в GitLab, вместе с сохранённым
`values.yaml`. Версия, которая в Harbor уже есть, не перезаписывается без
`-Force`. Это единственное, на что флаг влияет у этого скрипта.

**Перезалить версию, которая нигде не менялась.** Обычный случай: `5.1.0` лежит
и в GitHub, и в GitLab, и в Harbor, а копию в Harbor надо заменить. Синхронизация
с GitLab при этом ничего не найдёт и MR не откроет, но до Harbor прогон дойдёт, и
там решает `-Force`:

```powershell
# посмотреть, что версия уже в Harbor, и не трогать её
powershell -File deployments\scripts\transfer\sync-charts.ps1 -Charts namespace -PushToHarbor

# перезалить поверх существующего тега
powershell -File deployments\scripts\transfer\sync-charts.ps1 -Charts namespace -PushToHarbor -Force
```

Harbor принимает push на занятый тег: тег переезжает на новый артефакт, старый
остаётся в проекте без тега, пока его не уберёт сборка мусора реестра.

У чарта с зависимостями перед упаковкой проверяется, лежат ли они в Harbor в
нужной версии, и делается `helm dependency update`. Если зависимости нет, чарт
попадёт в отчёт как несделанный: в GitLab он уже уехал, а в Harbor нет.
Скачанные `charts/*.tgz` и `Chart.lock` остаются только во временном клоне и в
коммит не попадают.

Для self-signed сертификата добавь `-InsecureTls`: он действует на вызовы helm к
Harbor и на REST-запросы скрипта к Harbor и GitLab. На `git clone` он не
влияет, у git своя настройка (`http.sslVerify`).

### Доступы

Токен GitLab: `-GitLabToken` или `$env:GITLAB_TOKEN`. Подставляется только в URL
временного клона, который удаляется в конце, и никогда не пишется в конфиг.

Подойдёт personal access token, а также project или group access token, если он
покрывает все проекты чартов из карты. Нужное ему:

| | Что именно | Зачем |
|---|---|---|
| Scope | `write_repository` | клонировать проект и запушить ветку по https. `api` тоже подойдёт, он шире |
| Scope с `-AutoMerge` | `api` | найти MR после push, следить за его пайплайном и слить его |
| Роль | не ниже **Developer** в каждом проекте чарта | без неё нет ни push, ни создания MR |
| Роль с `-AutoMerge` | право сливать в `targetBranch` | обычно **Maintainer**: если целевая ветка защищена, Developer'у merge закрыт |

Права проверяются по факту: чарт, до проекта которого токен не дотянулся,
попадает в список неудач с причиной, а остальные переносятся. Отдельной проверки
прав заранее нет.

С `-AutoMerge` MR сливается от имени владельца токена, и в истории проекта чарта
это будет он. Для сервисного токена это то, что нужно, для личного - стоит иметь
в виду.

Harbor: берутся те же `HARBOR_USER` / `HARBOR_PASSWORD`, что и в первом
скрипте. Для `-PushToHarbor` учётной записи нужно право push в проект Harbor,
куда кладётся чарт (в Harbor это роль Developer и выше, либо робот с `push` и
`pull` на этом проекте). В любом прогоне той же учёткой скрипт спрашивает,
лежит ли в Harbor зависимость: для этого хватает права читать проект, а
публичный проект отвечает и анонимно.

GitHub: ничего. Оба репозитория публичные, архив скачивается анонимно, `gh`
используется, только если он уже установлен и авторизован.

## Требования

| Инструмент | Для чего |
|---|---|
| `docker` | `sync-images.ps1` целиком |
| `git` | `sync-charts.ps1` целиком |
| `helm` | только для `sync-charts.ps1 -PushToHarbor` |
| `gh` | не обязателен: ускоряет и авторизует загрузку с GitHub, при отсутствии используется публичный API |

`update-repos.ps1` не требует ничего сверх самого PowerShell и доступа к
github.com по https.
