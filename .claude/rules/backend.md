# Бэкенд: находки, за которые уже заплачено

Каждый пункт ниже - это чей-то разбор на несколько часов. Список ведём, чтобы
не платить второй раз: сверяйся с ним, когда пишешь новый вызов апстрима,
новое состояние заказа, новый фоновый цикл или новую таблицу.

Логи и метрики - в `observability.md`, переменные окружения - в `config.md`.

## База (унести в любой проект)

### Разговор с внешней системой

- **Первый ответ асинхронного апстрима - «ещё нет», а не «нет».** Мергабельность
  merge request'а считается после его создания, статус приложения приходит после
  синхронизации. Вердикт выносится по времени («не сдвинулось за N минут»), а не
  по первой попытке, иначе портал объявляет отказ там, где всё идёт нормально.
- **Незнакомое значение статуса - временное, а не поломка.** Список значений у
  апстрима длиннее, чем кажется, и пополняется без нас. Дефолт для неизвестного -
  «ещё думает»; «сломалось навсегда» назначается только явно перечисленным
  значениям.
- **Один и тот же код ответа скрывает разные случаи - ищи подробный статус.**
  GitLab отвечает 422 и на «пока нельзя слить», и на «не сольётся никогда»;
  различает их только `detailed_merge_status`. Прежде чем строить эвристику на
  коде и тексте, проверь, нет ли у апстрима поля, которое уже отвечает на вопрос.
- **`list` + `create` - это не upsert.** У большинства API нет «создай, если
  нет». Параллельный старт реплик или повторный запуск даёт дубли (у нас -
  дублирующиеся вебхуки, каждый MR доставлялся несколько раз). После создания
  нужен отдельный проход «оставить один», и он должен идти на каждом старте, а не
  только на первом.
- **Проверяй существование перед действием, а не только при показе.** Версия
  чарта, удалённая из registry, продолжала предлагаться к заказу и записываться в
  существующий заказ. Список для показа и допуск к действию должны считаться из
  одного места.
- **Недоступность апстрима не равна отсутствию данных.** Registry не ответил -
  каталог не пустеет: иначе разовый сбой читается как «все сервисы отозваны».
- **Внешняя система - источник истины, снимок в БД - кэш для интерфейса.** После
  конфликта состояние восстанавливается из неё (у нас - три стороны values из
  Git), а не накатывается поверх своей копией из базы: она не знает, что успело
  прилететь между делом.
- **Удаляй сам объект, а не запись о нём.** Argo CD без finalizer'а забирал
  Application, оставляя развёрнутое им работать в кластере, а портал считал
  отсутствие Application доказательством удаления. Если отсутствие записи для
  тебя доказательство - убедись, что оно правда доказательство.
- **Ошибка апстрима и ошибка домена - разные вещи.** `ErrUpstream` (502 с
  внятным текстом) отличается от `ErrNotFound` (404). Отдельный случай - 401/403
  от registry: это «роботу не выдали доступ», а не «чарта нет», и человеку нужно
  сказать именно это.

### Состояния и переходы

- **У каждого состояния должен быть выход.** Состояние без исходящего ребра
  когда-нибудь примет объект, для которого оно не задумывалось, и запрёт его
  насмерть. У нас в тупик «изменение отклонено» уезжал живой сервис: правка и
  отменённое удаление шли туда же, куда отклонённое создание.
- **Одно состояние - один смысл.** Если в состояние ведут два разных сюжета,
  интерфейс начинает их различать флагами, а восстановление невозможно. Дешевле
  развести состояния, чем таскать флаг.
- **«Мы уже об этом сказали» - это состояние, а не поле в памяти процесса.**
  Карта в процессе означает, что каждый рестарт заново рассылает те же
  уведомления. Место такому - строка в БД рядом с объектом.
- **Идентичность объекта во внешней системе повторяет идентичность в БД.** Имя
  Application было `{team}-{service}` при уникальности `(team, chart, service,
  cluster)`: два разных чарта с одинаковым именем сервиса породили два манифеста
  с одним именем CR, и два app-of-apps начали драться за один объект. Совпадение
  ключей проверяй буквально, поле в поле.

### Данные

- **`ON CONFLICT` под частичным уникальным индексом требует повторить его
  предикат.** Иначе Postgres не находит индекс и отвергает вставку целиком. У нас
  так молча не сохранилось ни одного уведомления.
- **То, что не ловится in-memory реализацией стора, покрывается тестом против
  настоящей БД.** У памяти нет SQL, значит она не может ошибиться в SQL. Такие
  тесты у нас идут по `STORE_TEST_URL` и пропускаются без него.
- **Смена статуса и её аудит - в одной транзакции.** Иначе сбой между ними
  меняет состояние и теряет след. Ошибку записи аудита не глотать: строка
  пропала навсегда, и это Error, а не тишина.
- **Колонки под чужие идентификаторы - сразу 64-битные.** id проекта и iid у
  большого GitLab выходят за int4.
- **Миграция не только меняет схему, но и чинит записи, которые уже застряли.**
  И пишет это в таймлайн объекта, чтобы прыжок из одного состояния в другое не
  выглядел мистикой.
- **Всё, что попадает в путь Git, имя объекта k8s или манифест, валидируется.**
  Кластер, namespace, имя сервиса - DNS-1123 и длина. Иначе `../` и перевод
  строки в поле уезжают в коммит.

### Фоновые циклы

- **Не глотать ошибку в фоне.** `_ = ...` в реконсайлере означает, что «MR не
  слился» становится недиагностируемым. Минимум - счётчик с причиной и лог.
- **Логировать край, а не каждый тик.** Флапающий апстрим на каждом тике даёт
  WARN. Пишем один WARN, когда цикл начал падать, и один INFO, когда поднялся;
  остальное в Debug. Метрики при этом пишутся на каждый тик - алерты считают по
  ним.
- **Backoff на упавший реконсайлер, таймаут на фоновый вызов, дренаж на
  выключении.** У фоновой работы нет дедлайна запроса, поэтому зависший запрос
  держит соединение пула вечно; выход из процесса посреди реконсиляции оставляет
  внешнюю систему в наполовину применённом состоянии.
- **Частичный сбой не отменяет весь проход.** Один недоступный namespace
  пропускается с логом, а не роняет сбор целиком.
- **Ограничение на повторы считается по причине, а не по объекту.** Лимит «три
  попытки» задумывался как «не гоняться за веткой, которая уезжает под одним
  изменением», а на деле рационировал, сколько раз вообще можно править заказ.
  Счётчик сбрасывается, когда изменение доехало.

### Больше одной реплики

Аудит перед масштабированием проще делать по готовому списку. Ломается обычно
одно и то же:

- **Счётчики и кэши в памяти процесса.** Событие приходит на ту реплику, которую
  выбрал ingress, а кнопка «проверить доставку» смотрит на свои счётчики: при N
  репликах она врёт в (N-1)/N случаев.
- **Данные, привязанные к процессу вместо сессии.** Сессии общие, человек ходит
  по всем репликам, а «улика» от его входа осталась там, где он логинился.
- **Всё, что решает лидер.** Если проверка привязана к лидеру, а её данные - к
  случайной реплике, проверка не срабатывает почти никогда.
- **Регистрация чего-либо во внешней системе на старте** (см. `list` + `create`).
- **Шина событий должна говорить, кто опубликовал событие.** Иначе то, что
  посчитано при получении, считается второй раз, когда возвращается по кругу.

Что переживает разделение само, если сделано так с самого начала: миграции под
advisory lock, запись под оптимистичной блокировкой (`version`), уведомления с
dedup-ключом и уникальным индексом под ним, сессии в общем кэше.

### Безопасность

- **Фильтр в списке - не авторизация.** Список фильтровался по видимости, а
  чтение конкретного объекта по URL - нет. Скрытое отдаём как 404, а не 403:
  403 подтверждает, что объект существует.
- **Привилегированная группа сравнивается полным путём, а не сегментом.**
  Совпадение по любому сегменту означает, что кто угодно, кто может создать
  подгруппу с нужным именем, становится админом.
- **Скаляры, подставляемые в YAML-шаблон, экранируются.** Значение с переводом
  строки или спецсимволом ломает или подделывает структуру манифеста.
- **Тестовая заглушка исключается из прод-сборки build-тегом, а не флагом
  конфигурации.** dev-аутентификатор, выдающий любую роль по заголовку, должен
  физически отсутствовать в бинаре.
- **Скачанный артефакт сверяется с digest'ом из манифеста**, а имена из манифеста
  проверяются перед подстановкой в URL registry.
- **Секрет по умолчанию - отказ стартовать.** Не предупреждение.
- **Внутренняя ошибка апстрима не уходит наружу дословно** (хосты, порты,
  драйверы). Детали в лог, наружу общая формулировка.

### Конфигурация и тесты-скобы

- **Обязательность переменной живёт в теге (`required,notEmpty`), а не в
  проверках в `main`.** Тогда загрузчик называет все недостающие разом и до того,
  как что-то запущено.
- **Две стороны одной вещи держатся тестом.** Переменная и её описание, фоновый
  цикл и его строка на странице состояния, генератор и сгенерированный файл. Тест
  падает и когда одной стороны нет, и когда есть лишняя. Это дешёвый способ не
  разъезжаться со временем: заводя новую пару такого рода, сразу заводи скобу.

## В этом проекте

- **Заглушки апстримов (`internal/*/fake.go`) - только для тестов.** Включить их
  конфигурацией нельзя, портал всегда работает с настоящими Harbor, GitLab и
  Argo CD.
- **Git - источник истины для values, `values_yaml` в БД - снимок для UI.** Drift
  и pull синхронизируют снимок с Git, не наоборот.
- **Один открытый MR на заказ** плюс оптимистичная блокировка по `version`.
- **Values сливаются как дерево полей, а не как текст.** Три стороны берутся из
  Git (база из `diff_refs.base_sha`, «их» из целевой ветки, «моё» из исходной);
  поле, которое двигала одна сторона, берётся у неё, одинаковое движение обеих
  сторон - согласие, остальное - настоящее разногласие и называется по имени.
  Списки сравниваются целиком: позиция в них несёт смысл.
- **Группа админов - не команда.** Она даёт роль и не попадает в список команд, а
  значит адресовать ей уведомление как команде - значит не адресовать никому.
- **Аудитория уведомления вычисляется на чтении**, поэтому новый читатель
  получает всю историю рассылок «для всех». Под каждую аудиторию читателя пишется
  «пол» - момент, с которого он её видит.
