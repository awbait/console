# Changelog

Пиши для человека, который пользуется продуктом и не читал код или PR.
Из записи должно быть понятно, что изменилось, где это видно и требуется ли
что-нибудь сделать.

## Сначала определи правила проекта

Перед редактированием прочитай инструкции репозитория, существующий журнал
и README папки ожидающих записей, если она есть. Установи:

- где находятся журналы и ожидающие записи;
- какие языки нужны и как устроен файл отдельной записи;
- какие категории и формат версий приняты;
- есть ли команда предварительного просмотра и сборки релиза;
- как проект создаёт ветки, PR и опубликованные release notes.

Не считай `changelog.d/`, два языка или команду `make changelog` обязательными.
Это возможные соглашения проекта. Не заменяй работающий сборщик без запроса.

Если соглашений нет, используй `CHANGELOG.md` и отдельные Markdown-записи
в `changelog.d/`: одна запись на изменение, содержательное уникальное имя файла.
Язык бери из документации проекта или запроса пользователя; дополнительные
переводы без необходимости не добавляй. Для нового журнала используй категории
и заголовки версий из раздела «Сборка релиза».

Если в проекте ещё нет формата отдельных записей, используй такой:

```markdown
### Fixed

Исправили сохранение настроек на странице профиля.
```

Если нужны несколько языков, разделяй тексты заголовками `#### ru`, `#### en`
под общей категорией. При сборке они станут отдельными пунктами в журналах
своего языка. Существующий формат проекта имеет приоритет над этим примером.

## Когда нужна запись

Запись нужна для новой возможности, изменения поведения, исправления доступной
пользователю ошибки, безопасности, удаления функции или нового требования
к использованию продукта. Добавляй её вместе с изменением.

Не записывай рефакторинг, тесты, сборку, внутренние переименования и обновление
инструкций, если для пользователя ничего не изменилось.

Одно самостоятельное изменение описывай одной записью. Не раскладывай одну
ошибку на записи о причине, исправлении и обработке старых данных.
Для нескольких продуктов или компонентов соблюдай границы их журналов.

## Как написать запись

1. Установи факты по изменению: какой экран или действие затронуто, что теперь
   доступно или какая ошибка исправлена, при каких условиях.
2. Назови видимый результат обычными словами. Не переноси в запись объяснение
   работы кода и не копируй заголовок коммита.
3. Напиши текст на основном языке журнала. Если нужны переводы, передай тот же
   смысл естественными предложениями на каждом языке.
4. Прочитай запись отдельно от исходного описания по проверке ниже.

Если неясно, что пользователь увидит, вернись к изменению. Не заполняй пробел
фразами «улучшили работу», «исправили обработку» или выдуманным результатом.

## Тон и язык

- **Спокойно и конкретно.** «Добавили», «Исправили», «Убрали», «Перенесли».
  Для новой возможности подходит «Теперь можно…». «Улучшили» требует
  объяснения конкретного изменения.
- **Называй место или действие.** «В форме заказа», «в таблице заказов»,
  «при установке». Для лицензии или настройки называй документ или параметр,
  не придумывай экран.
- **Обычно достаточно одного предложения.** Второе короткое предложение
  допустимо для необходимого условия или действия пользователя. Не склеивай
  несколько мыслей двоеточием ради формального ограничения длины.
- **Сохраняй важные условия.** Если ошибка возникала только при смене версии,
  это должно остаться в тексте. Не обещай поддержку любых случаев или успешное
  завершение, если исправление этого не гарантирует.
- **Описывай изменение, а не историю работы.** Не добавляй рассказ о поиске
  причины и решении команды. Не приписывай пользователям поведение и эмоции,
  которых никто не проверял. Прошедшее время в слове «Исправили» нормально.
- **Выбирай прямые выражения.** «Включить или выключить поле» понятнее, чем
  «сказать, в какую сторону его переключить». «Значения по умолчанию» понятнее,
  чем «значения, которые чарт отвечает сам».
- **Не заставляй угадывать предмет.** «Настройка, которую задаёт другая
  настройка» не объясняет исправление. Местоимения «это», «её», «его» используй
  только там, где понятно, к какому предмету они относятся.
- **Без канцелярита и образных оборотов.** Не пиши «осуществляется обработка»,
  «повышена корректность», «обновление остановилось на полпути», «данные доехали».
  Назови действие или ошибку напрямую.
- **Без устройства реализации.** Функции, пути схемы, таблицы БД, внутренние
  флаги и номера коммитов не объясняют изменение пользователю. Термины,
  которые есть в интерфейсе или документации, оставляй, если они необходимы
  для понимания действия или условия.
- **Названия должны совпадать с интерфейсом.** Не подменяй подпись поля его
  внутренним идентификатором. Точные параметры конфигурации сохраняй, когда
  пользователь должен ввести их сам.
- **Не усложняй пунктуацию.** Не используй длинное тире и цепочки уточнений.
  Если фразу приходится расшифровывать, перепиши её.

## Примеры

Примеры показывают форму текста. Применяй их смысл только к изменениям,
которые действительно дают описанный результат.

| Неясно | Понятно |
| --- | --- |
| Исправили сообщение для настройки, которую задаёт другая настройка: форма называет её так же, как подписано поле, и говорит, как его переключить. | Исправили сообщения об ошибках в форме заказа: они показывают название поля и подсказывают, нужно его включить или выключить. |
| Исправили пустые формы для настроек, которые лежат во вложенном сабчарте. | Исправили отображение настроек вложенных компонентов в форме заказа и карточке сервиса. |
| Портал сам повторяет применение изменений, не дожидаясь команды синхронизации. | Добавили автоматическую повторную попытку развёртывания при обновлении сервиса. |
| Меню сохраняет единую геометрию при сворачивании. | Выровняли иконки в свёрнутом боковом меню. |
| Улучшили обработку ошибок. | Добавили причину ошибки развёртывания на страницу заказа. |

Необходимую инструкцию можно отделить:

> Добавили кнопку «Перечитать чарт» на странице управления чартом.
> Используйте её после повторной публикации той же версии в Harbor.

## Переводы

Все языки должны описывать одинаковое изменение, условия и ограничения.
Не переводи неясный исходник буквально: сначала установи, что произошло.
Порядок слов и конструкция предложения могут различаться.

Английский текст тоже должен быть понятен сам по себе. Вместо
`a setting that another setting decides` назови результат:
`Error messages in the order form use the field label and say whether to
turn the field on or off.`

Каждый текст пиши целиком на своём языке, включая названия кнопок и страниц,
если проект не устанавливает другой порядок. Названия продуктов и точные
идентификаторы сохраняй. Не добавляй в перевод новые возможности и обещания.

## Проверка текста

Перед сохранением прочитай запись как отдельный пункт журнала:

- Без PR и кода понятно, что изменилось и где это видно?
- Названы конкретные действия и ошибки, понятны все местоимения?
- Описан результат для пользователя, а не связи между частями кода?
- Сохранены важные условия, нет фактов и обещаний сверх сделанного?
- Фразу легко прочитать с первого раза, её не приходится мысленно переводить?
- Переводы совпадают по смыслу?
- Понятно, что делать, если от пользователя требуется действие?

Если ответ «нет», перепиши запись. Затем выполни существующую проверку формата
или предварительный просмотр журнала. Такая проверка не оценивает понятность
текста и не заменяет его чтение.

## Сборка релиза

Готовь релиз только по явному запросу пользователя. Запрос исправить текст
журнала не означает запрос выпустить версию. Соблюдай процесс Git и публикации
конкретного проекта.

1. Прочитай ожидающие записи. Удали дубли одного изменения и исправь неясный
   текст. Не восстанавливай журнал из одних заголовков коммитов.
2. Выбери версию по принятой в проекте схеме. Для SemVer: совместимая новая
   возможность повышает MINOR, исправления повышают PATCH, несовместимое
   изменение повышает MAJOR. До `1.0.0` учитывай практику проекта.
   Для несовместимого изменения назови замену или необходимое действие.
3. Если есть сборщик, используй его: например, `make changelog RELEASE=X.Y.Z`.
   Сначала проверь назначение команды в проекте. Не создавай Makefile ради
   скилла и не предполагай, что пример команды существует в другом репозитории.
4. Если сборщика нет, выполни сборку редактированием: прочитай ожидающие записи,
   вставь новую секцию в каждый журнал, сохрани старые секции и проверь перенос
   всех выбранных записей. Только после проверки удали использованные файлы
   записей. Не удаляй README, саму папку и записи, не вошедшие в релиз.
   Если проект хранит ожидание в `Unreleased`, перенеси соответствующие пункты
   оттуда вместо создания второй системы.
5. Для нового журнала используй заголовок `## [X.Y.Z] - YYYY-MM-DD`,
   новые версии сверху и непустые категории в порядке `Added`, `Changed`,
   `Deprecated`, `Removed`, `Fixed`, `Security`.
   Русские названия: «Добавлено», «Изменено», «Устарело», «Удалено»,
   «Исправлено», «Безопасность».
6. После заголовка версии сразу идут категории. Не добавляй вступительную
   сводку вроде «Релиз про заказ и обновление сервиса» ни на одном языке.
7. Проверь совпадение версий, дат, категорий и порядка записей в переводах.
   Обнови ссылки сравнения версий, если журнал их использует.

Уже выпущенные записи меняй только для исправления ошибки или непонятного
текста, сохраняя смысл изменения. Исправляй переводы вместе. Если из журнала
уже опубликованы release notes, учти их в исправлении по процессу проекта.
