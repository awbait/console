# Уникальность имён Argo CD Application между кластерами

Статус: решение по #523 реализовано. Ниже сохранён анализ исходной ошибки и выбранного подхода. Новый шаблон применяется к новым заказам и редактируемым черновикам. Существующие заказы сохраняют записанные имена и пути в Git.

## Проблема

На одном стенде пользователи заказывают один и тот же сервис в один и тот же
namespace, но в разные кластеры. Это допустимые и независимые заказы. В Git для
них создаются разные файлы `application.yaml`, но `metadata.name` внутри файлов
совпадает.

Если эти файлы применяет один Argo CD в одном namespace Application, оба
манифеста описывают один объект вместо двух.

Пример:

| Поле | Заказ 1 | Заказ 2 |
| --- | --- | --- |
| Стенд | `edp` | `edp` |
| Команда | `core` | `core` |
| Чарт | `postgres` | `postgres` |
| Namespace | `payments` | `payments` |
| Имя сервиса | `db` | `db` |
| Кластер | `dev` | `stage` |
| Путь в Git | `dev/payments/db` | `stage/payments/db` |
| Текущее имя Application | `core-postgres-payments-db-edp` | `core-postgres-payments-db-edp` |

## Причина

Части системы согласованы между собой, кроме генератора имени Application и его
защитной проверки.

1. **База разрешает такие заказы.** Уникальный индекс `uniq_active_service`
   включает стенд, команду, чарт, имя сервиса, кластер и эффективный namespace
   (`internal/store/migrations/000035_order_identity_per_stand.sql:10`). Заказы
   из примера различаются кластером, поэтому конфликта в БД нет.
2. **Пути в Git различаются.** `NewInstancePath` всегда добавляет кластер и
   namespace в путь (`internal/provisioning/gitops.go:267`). Файлы не
   перезаписывают друг друга.
3. **Шаблон имени не содержит кластер.** Текущее значение по умолчанию
   (`internal/config/config.go:151`):

   ```gotemplate
   {{.Team}}-{{.Chart}}-{{.Namespace}}-{{.ServiceName}}{{if .Stand}}-{{.Stand}}{{end}}
   ```

4. **Генератор не передаёт кластер в шаблон.** В общем `tmplData` поле
   `Cluster` есть, но `AppName` заполняет только команду, чарт, namespace,
   сервис и стенд (`internal/provisioning/gitops.go:192`). Поэтому даже ручное
   добавление `{{.Cluster}}` в настройку сейчас даст пустой постфикс.
5. **Проверка дубликатов пропускает один стенд.** `checkAppName` исключает
   заказ, у которого совпал `StandID`
   (`internal/provisioning/service.go:495`). Она останавливает только повтор
   имени между разными стендами, добавленный в #455.
6. **Проверка конфигурации не проверяет кластер.** `appNameTemplate`
   сравнивает варианты сервиса, namespace, команды, чарта и стенда
   (`internal/checks/static.go:119`). Поле `Cluster` в тестовых данных есть,
   но отдельного случая для него нет.

Это тот же класс ошибки, что в #304 и #455: идентичность заказа в БД и Git
отличается от идентичности создаваемого внешнего объекта. В #304 добавили
namespace, в #455 добавили стенд, но кластер в имя не попал.

## Последствия

У двух заказов совпадает не только отображаемое имя. Совпадает Kubernetes
идентичность `(metadata.namespace, metadata.name)` объекта Application.

- Argo CD получает два источника одного Application. Destination, sources и
  values могут переключаться между заказами по результатам применения
  манифестов.
- Оба заказа хранят один `argocd_app_name`, поэтому reconcile портала читает для
  них один и тот же объект Argo CD.
- Удаление или изменение одного манифеста может повлиять на Application другого
  заказа. Наличие resources finalizer делает автоматическую миграцию таких
  конфликтов особенно опасной: удаление Application может запустить удаление
  ресурсов.

Конкретную последовательность перезаписи и удаления нужно смотреть на
фактической схеме app-of-apps инсталляции. Для решения достаточно уже того,
что две GitOps-записи претендуют на один Application.

## Ограничения решения

- Имя Application вычисляется при создании заказа и хранится в
  `requests.argocd_app_name`. Смена шаблона не переименует существующие заказы.
- У живого заказа стенд и кластер неизменны. Черновик может менять оба поля,
  поэтому имя черновика пересчитывается при редактировании.
- Импорт сохраняет `metadata.name` найденного манифеста. Он не должен
  переименовывать чужие Application.
- Кластер нового заказа уже проверен как DNS-метка длиной до 63 символов, его
  можно безопасно подставлять в имя.
- Стенд нужно сохранить в шаблоне. Убрать его после добавления кластера нельзя,
  иначе вернётся коллизия #455 между стендами.
- Helm использует имя Application как имя релиза, если `helm.releaseName` не
  задан. Лимит имени релиза: 53 символа. Поэтому новые имена длиннее 53 символов
  сокращаются до читаемого префикса длиной до 36 символов и постфикса из дефиса
  и первых 16 шестнадцатеричных символов SHA-256 полного имени. Конечные дефисы
  и точки префикса убираются. Хеш учитывает кластер и стенд, даже если они не
  попали в префикс. Повтор итогового имени по-прежнему отклоняется проверкой
  коллизий. Короткие имена не меняются. Сохранённые имена при обновлении и
  импорте не сокращаются автоматически, чтобы не переименовывать ресурсы.
  См. [Argo CD Helm release name](https://argo-cd.readthedocs.io/en/stable/user-guide/helm/#helm-release-name)
  и [валидатор Helm](https://github.com/helm/helm/blob/v3.17.3/pkg/chartutil/validate_name.go).

## Варианты

### 1. Добавить кластер в шаблон и расширить защиту от дубликатов

Предлагаемый шаблон по умолчанию:

```gotemplate
{{.Team}}-{{.Chart}}-{{.Namespace}}-{{.ServiceName}}{{if .Cluster}}-{{.Cluster}}{{end}}{{if .Stand}}-{{.Stand}}{{end}}
```

Для примера выше получатся имена:

```text
core-postgres-payments-db-dev-edp
core-postgres-payments-db-stage-edp
```

`Cluster` делается условным только для совместимости со старыми данными и
ручными вызовами. Новый заказ всегда получает кластер через `orderCluster`.

Одновременно нужно расширить `checkAppName`: сравнивать живые заказы независимо
от стенда, если их Application попадают в один namespace Argo CD. Это защищает
от пользовательского шаблона без кластера и от неочевидных совпадений при
склейке компонентов через дефис.

Плюсы:

- устраняет именно исходный сценарий;
- имя остаётся читаемым и объясняет, где находится сервис;
- повторяет уже принятые решения #304 и #455;
- не требует миграции БД и переименования существующих заказов.

Минусы:

- имя становится длиннее;
- предпроверка в БД не является транзакционной гарантией при одновременном
  создании двух заказов, как и существующая проверка #455.

### 2. Добавлять ID заказа или хеш полной идентичности

Например, короткий хеш `(stand, team, chart, namespace, service, cluster)`.

Плюсы: постфикс имеет фиксированную длину и покрывает любые различия заказов.

Минусы: имя менее читаемо, короткий хеш всё равно требует проверки коллизий, а
полный UUID заметно увеличивает имя. Для текущей ошибки это более крупная смена
контракта именования без необходимости.

### 3. Только запрещать повтор имени

Можно расширить `checkAppName`, не меняя шаблон. Это предотвратит конфликт в
Argo CD, но не позволит заказать одинаковый сервис в разные кластеры, то есть
откажется от допустимого сценария. Как самостоятельное решение не подходит.

### 4. Разводить кластеры по namespace Argo CD

Отдельные namespace Application устраняют пересечение Kubernetes идентичностей,
но требуют другой эксплуатационной топологии и не исправляют генератор. Это
вариант изоляции инсталляции, а не исправление портала.

## Рекомендация

Выбрать вариант 1.

### Изменения реализации

1. Передавать `r.Cluster` в `AppName` и дальше в `tmplData.Cluster` при
   создании заказа, редактировании черновика и вычислении fallback при импорте.
2. Изменить шаблон по умолчанию на вариант с `.Cluster`, сохранив `.Stand`.
3. Обновить `.env.example` генератором конфигурации и примеры в документации.
4. Добавить в `appNameTemplate` сравнение двух кластеров. Шаблон без кластера
   считать ошибочным: он молча объединяет допустимые заказы одного стенда.
5. Убрать исключение одного стенда из `checkAppName`. Разные namespace Argo CD
   по-прежнему могут содержать Application с одинаковыми именами.
6. Оставить существующие `argocd_app_name` и `instance_path` без миграции.

### Проверки

- Два одинаковых заказа в разных кластерах одного стенда получают разные имена
  Application и разные пути в Git.
- Повтор в том же кластере и namespace по-прежнему отклоняется ключом заказа.
- Пользовательский шаблон без кластера не пропускает второй такой заказ в Git.
- Одинаковые имена в разных namespace Argo CD остаются допустимыми.
- При смене кластера черновика имя пересчитывается с новым постфиксом.
- После отправки заказа последующие обновления сохраняют записанное имя.
- Импорт сохраняет имя из найденного манифеста.
- Статическая проверка конфигурации различает шаблоны с кластером и без него.

## Существующие конфликты и временный обход

Автоматически исправлять уже созданные пары не предлагается. Сначала нужно
сверить `argocd_app_name`, файлы в Git и фактические Application инсталляции,
затем составить отдельный план для каждого конфликта с учётом resources
finalizer.

Для установок без исправления временный обход: различать имена сервисов или
namespace между кластерами. После обновления стандартный шаблон уже содержит
`{{.Cluster}}`. Если `ARGOCD_APP_NAME_TEMPLATE` задан явно, в него нужно добавить
`{{if .Cluster}}-{{.Cluster}}{{end}}`, сохранив постфикс стенда. Это изменит имена
новых заказов, но не переименует существующие Application.
